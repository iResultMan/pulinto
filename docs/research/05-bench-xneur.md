# Замер качества автоопределения раскладки в xneur 0.20.0

Конкурентный замер на эталонном корпусе `docs/research/corpus/golden.tsv`
(2300 примеров). Цель — понять, насколько хорош каскад xneur `check_lang`,
прежде чем решать, стоит ли продолжать собственную разработку.

**Главный вывод: xneur 0.20.0 дает 96.7% accuracy на корпусе, но ложные
срабатывания (самая дорогая ошибка) сконцентрированы в конкретных, предсказуемых
местах — короткие слова (1-2 символа) и Cyrillic-аббревиатуры/коды — а не
размазаны случайно по всему корпусу.**

---

## 1. Как мерили: две попытки, честно про обе

### Попытка А (точная, через реальный libxneur) — не взлетела, зафиксировано почему

В процессе работы в систему поставили `libxneur-dev` (заголовки
`/usr/include/xneur/{xneur,xnconfig,list_char}.h`, `pkg-config xneur`).
Публичный API (`xneur_handle_create`, `xneur_get_layout`, `xneur_get_word`)
дает ровно то, что нужно, а живой X-сеанс уже сконфигурирован с двумя
раскладками (`setxkbmap -query` → `layout: ru,us`), т.е. `xneur_handle_create()`
подхватывает обе раскладки без каких-либо правок системных настроек.

Собран C-харнесс (`docs/research/corpus/bench_xneur_variant_a_attempt.c`),
который:
- создает `handle` через `xneur_handle_create()`;
- инициализирует `main_window` через экспортированную (но не публично
  задокументированную) `window_init(handle)`;
- временно блокирует нужную группу раскладки через экспортированную
  `set_keyboard_group()` (то же самое, что делает хоткей Alt+Shift — обратимое,
  штатное действие, конфигурация клавиатуры не меняется) и восстанавливает
  исходную группу по окончании;
- вызывает `xneur_get_word(handle, word)` — ту самую публичную функцию,
  которая внутри дергает `check_lang()`.

Компилируется и создает `handle` без ошибок (`total_languages=2`, `ru`/`us`
опознаны корректно). Но **первый же вызов `xneur_get_word` падает с SIGSEGV**
внутри `XkbGetState()` (см. `gdb` backtrace ниже). Проверено и исключено самое
очевидное объяснение — "не сделан XKB extension negotiation": изолированный
тест голого `XOpenDisplay` + `XkbGetState()` на этом же дисплее **не падает**.
Значит падение вызвано состоянием, которое портит сам `xneur_handle_create`/
`window_init` при вызове вне полного event-loop демона (вероятно, повреждение
кучи в этой сборке — практика ручных malloc/realloc в `xneurlib.c` местами
рискованная). Пойти дальше можно было бы только угадав раскладку полей
непубличных структур `struct _window` / `struct _buffer` (их нет в
поставляемом заголовке) — а сторонний клон исходников на GitHub уже дал
**несовпадающее** смещение полей при проверке через `gdb`, то есть чинить
падение пришлось бы вслепую, ABI-угадыванием. Это ровно тот случай, когда
результат может стать тихо неверным, а не просто упасть, — по прямому
требованию задачи такой риск неприемлем. На этом попытка А остановлена.


### Попытка Б (использована для чисел в этом отчете)

Точное воспроизведение каскада `check_lang` (`xneur/lib/ai/detection.c`) на
**настоящих данных этой же версии xneur**, без запуска самого бинаря:

| Компонент | Источник |
|---|---|
| Позиционные таблицы раскладок (retype qwerty↔йцукен) | `crates/pulinto-core/src/layout.rs` (уже покрыты тестами проекта) |
| regex-словарь (ступень 1) | `/usr/share/xneur/languages/{ru,en}/dictionary`, компилируется как есть |
| Орфография (ступень 2) | **настоящий `libenchant-2.so.2`** — тот же файл, что подтвержден в `NEEDED` у `libxneur.so.20` через `readelf`/`ldd`/`nm`. Вызывается напрямую через `ctypes` по `enchant_dict_check()` |
| Биграммы/триграммы (ступени 4-5) | `/usr/share/xneur/languages/{ru,en}/proto`, `proto3`, бинарное вето «ноль попаданий», без суммирования штрафов |

Скрипт: `docs/research/corpus/bench_xneur.py`.

**Важная находка по факту установленного бинаря.** `readelf -d libxneur.so.20`
показывает `NEEDED libenchant-2.so.2`, символов `aspell` в бинаре нет вообще
(`strings | grep aspell` — пусто). Значит эта сборка (`0.20.0-3.3build1`,
Ubuntu) скомпилирована `WITH_ENCHANT` и **без** `WITH_ASPELL` — ступень aspell
в `check_lang` физически не выполняется (она под `#ifdef WITH_ASPELL`).
Устанавливать и подключать отдельно `aspell-ru` для этого замера было бы
**неверно**: реальный xneur его не спрашивает. Правильная ступень
орфографии — enchant, и она реализована через настоящую библиотеку, а не
через приближение.

**Важная находка по CLI-обвязке enchant.** Первая реализация дергала
`enchant-2 -a` (ispell-pipe режим) и парсила ответ построчно. Это дало
результаты, которые выглядели правдоподобно, но были тихо неверны: CLI в этом
режиме сам **токенизирует строку по пунктуации** — слово `ht,`yjr` (после
digit/punct-препроцессинга, где `` ` `` — позиция буквы «ё») дало на выходе
ДВА блока ответа («ht» — валидно, «yjr» — нет) вместо одного, из-за чего
построчный парсер съезжал и портил результат для последующих слов в батче.
Обнаружено сравнением до/после (accuracy на `password` выросла с 80.0% до
98.3%, на `prose_ru` — с 97.6% до 99.9% после исправления). Исправлено прямым
вызовом `enchant_dict_check()` через `ctypes` по `libenchant-2.so.2` —
атомарная проверка всей строки без токенизации, ровно как делает сам xneur в
`get_enchant_hits()`. Все числа ниже — после исправления.

### Что осознанно опущено

- **Ступень «похожие слова по Левенштейну» (`get_similar_words`) не
  реализована.** Но это не снижает достоверность: сам публичный API xneur
  (`xneur_get_layout`/`xneur_get_word`, см. `xneurlib.c`) вызывает
  `check_lang(handle, buffer, cur_lang, FALSE)` — с `check_similar_words =
  FALSE`. То есть эта ступень отключена и в «настоящем» xneur при обращении
  через штатный публичный интерфейс.
- **`cur_lang`** (активная раскладка в момент набора слова) не наблюдаема из
  TSV напрямую — восстанавливается эвристикой по алфавиту `input`
  (есть кириллица без латиницы → `ru`, есть латиница без кириллицы → `us`,
  иначе по умолчанию `us`). Для корпуса это оказалось однозначным почти во
  всех случаях (input — либо целиком кириллица, либо целиком латиница), но
  формально это допущение, а не наблюдаемый факт.
- Раскладка `en`/`us` в данных xneur физически идентична (одинаковый размер
  файлов `dictionary`/`proto`/`proto3`), используется как один язык.

## 3. Разбор характерных ошибок

### 3.1. Однобуквенные слова (`short1`, 64.2% — худшая категория)

Структурная дыра, не случайность. В `ru/dictionary` зашито 8 регулярок на
однобуквенные слова (`а б в ж и к о с у я` — если точнее, `а в и к ну о у я`;
у английского **вообще нет** ни одной такой записи). Ступень regex-словаря
проверяет ВСЕ языки без учета контекста: если английская буква, будучи
переложена на клавиатурные позиции ru, попадает в этот список — она
конвертируется гарантированно и всегда, что бы ни стояло рядом:

```
j -> о   f -> а   b -> и   z -> я   r -> к   d -> в   e -> у
```

Это ровно 7 английских букв, которые xneur никогда не сможет оставить в
покое, если они встретились как отдельное «слово» (переменная, инициал,
список через запятую и т.п.) — независимо от контекста. Пример из корпуса:
`f` в контексте `мама сказала` ожидаемо `KEEP` (это реальная английская буква
`f`), xneur конвертирует её в `а`.

Обратная сторона той же дыры — пропуски: у английского словаря НЕТ
однобуквенных записей, а биграммная/триграммная ступень математически не
работает на словах короче своей длины (`len < proto_len` → сразу
`NO_LANGUAGE`). Поэтому для однобуквенных русских слов, набранных в
английской раскладке (`,` → `б`, `;` → `ж`, `c` → `с`, `'` → `э`), ни одна
ступень каскада не срабатывает вообще — решение падает в `NO_LANGUAGE`, что
по факту всегда означает `KEEP`. Из 76 решений «ничего не сработало» **34%
оказались неверными** — это самый ненадежный узел каскада.

### 3.2. Двухбуквенные слова (`short2`, 79.2%)

Тот же класс проблемы, но через ступень enchant, а не словарь: короткие
русские слова, чья qwerty-перекладка случайно образует настоящее короткое
английское слово, конвертируются ложно:

```
ща -> of    щр -> oh    щл -> ok    шы -> is    гз -> up    щт -> on
```

И наоборот — двухбуквенные искажения не распознаются, если целевое слово не
попало в словарь enchant для нужного языка (`kb` → ожидалось `ли`, `vs` →
ожидалось `мы`, и т.д.). Двухбуквенные словоформы — зона, где словарная
проверка принципиально не может учитывать контекст, а вероятность случайного
совпадения «валидное слово в обоих языках» на таких коротких строках высока
статистически.

### 3.3. Аббревиатуры и буквенно-цифровые коды (`abbrev` 95%, `number` 90%)

```
ЕС -> TC     ТВ -> ND     3D -> 3В     Т-34 -> N-34     АК-47 -> FR-47
```

Механизм для `3D`: препроцессинг xneur отрезает хвостовые цифры и пропускает
ведущие цифры/пунктуацию — в `3D` от «слова» для регекс-проверки остается
буква `D`, которая через ту же дыру п.3.1 конвертируется в `В`. Для
двухбуквенных кириллических аббревиатур (`ЕС`, `ТВ`) их латинская
перекладка (`TC`, `ND`) — это ровно тот же эффект «случайно валидное слово»,
что и в п.3.2, только на уровне ступени enchant для двух заглавных букв
(словари enchant/hunspell нередко трактуют неизвестные ALL-CAPS токены как
вероятные акронимы и пропускают их).

### 3.4. Пароли (`password`, 98.3%, 1 ошибка из 60)

Единственная ошибка — `Qaz2wsx!@` → `Йфя2цыч!"`: намеренно «клавиатурный»
пароль (буквы подряд по рядам клавиатуры), пойманный на ступени биграмм —
цепочка `Qaz2wsx` при отрезании цифр/пунктуации превращается в короткий
остаток, который совпал с запрещенной биграммой английского языка. В
остальных 59 паролях (включая смешанные регистр+цифры+спецсимволы) каскад
корректно не трогает пароль — сильная сторона (пароли почти никогда не
образуют ни валидных словарных слов, ни чистых от биграмм остатков в обоих
языках одновременно).

### 3.5. Единственный пропуск в прозе: `dyer` → ожидалось `внук`

Иллюстрация фундаментального, неустранимого класса ошибок словарного
подхода: искаженное кириллическое слово `dyer` (задумано `внук`, набрано в
английской раскладке) само по себе оказывается настоящим английским словом
(«dyer» — красильщик). Ступень enchant видит валидное английское слово в
`cur_lang=us` и сразу возвращает `KEEP` — с точки зрения чистого
орфографического каскада это неотличимо от честного `dyer`. Никакая
словарная проверка без учета контекста здесь не поможет.

## 4. Вывод

**Сильные стороны xneur:** обычная связная проза (`prose_ru`/`prose_en`,
100.0%/99.9%), явно структурированные строки — URL, код, транслит, смешанные
слова (`url`/`code`/`translit`/`mixed`/`name`, 100.0%) и пароли (98.3%) —
каскад практически не трогает. Общая accuracy 96.7% на 2300 примерах —
сильный базовый результат.

**Слабые места, все — системные, а не случайный шум:**
1. **Однобуквенные слова (`short1`, 64.2%)** — асимметрия словарных списков
   (8 записей у ru, 0 у en) создает набор из 7 английских букв, которые
   гарантированно конвертируются неверно, и одновременно оставляет часть
   однобуквенных русских слов вообще без защиты (ни одна ступень не
   срабатывает).
2. **Двухбуквенные слова (`short2`, 79.2%)** — на такой длине высока частота
   случайных совпадений «валидное слово в обеих раскладках», словарная
   проверка без контекста здесь принципиально ненадежна.
3. **Аббревиатуры/буквенно-цифровые коды (90-95%)** — тот же эффект, что и
   short1/short2, проявляется после агрессивного цифро-пунктуационного
   препроцессинга, оставляющего короткий остаток.
4. Ложные срабатывания (2.4% от `KEEP`) сконцентрированы почти целиком в
   short1/short2/abbrev/number/password (35 из 41) — то есть предсказуемы и
   потенциально устранимы точечно (контекстные правила именно для коротких
   токенов), а не разбросаны по всему корпусу непредсказуемо.

Для решения о продолжении собственной разработки: xneur — сильный
конкурентный ориентир на обычном тексте, но у него есть точный,
воспроизводимый набор слабых мест (короткие токены, коды/аббревиатуры) —
именно там, где `docs/ALGORITHM.md` этого проекта уже предлагает отдельные
ступени (явные таблицы коротких слов + контекстное согласие, см. §3 того
документа). Это дает конкретную, измеримую цель для улучшения, а не только
абстрактное «сделать лучше».

## 5. Ограничения замера

- Численные результаты выше получены **Вариантом Б** (воспроизведение
  каскада на данных xneur + настоящий `libenchant-2.so.2`), не прямым вызовом
  скомпилированного `xneur`. Попытка А (см. §1) уперлась в сегфолт внутри
  `libX11`, воспроизводимый и задокументированный, но не устраненный без
  риска ABI-угадывания.
- Ступень «похожие слова по Левенштейну» не реализована — но это совпадает с
  поведением настоящего публичного API xneur (`check_similar_words=FALSE`),
  не является упрощением с нашей стороны.
- `cur_lang` восстановлен эвристикой по алфавиту `input`, а не получен из
  колонки корпуса — для этого корпуса эвристика однозначна (input всегда
  либо целиком кириллица, либо целиком латиница), но это допущение.
- Мы не варьировали `handle->languages[].excluded`/`disable_auto_detection`
  и не проверяли поведение при других наборах языков (более двух раскладок) —
  корпус и этот замер рассчитаны на пару ru/us, как в реальном использовании
  PuLinTo.
