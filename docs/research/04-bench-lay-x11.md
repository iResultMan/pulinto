# Бенчмарк lay-x11 на эталонном корпусе

Конкурентный анализ: `HelpFreedom/lay-x11` (форк `radislabus-star/lay-public` под X11),
Rust, MIT. Задача — измерить качество **автоматического** определения
«написано не в той раскладке» на корпусе `docs/research/corpus/golden.tsv`
(2300 примеров, KEEP/CONVERT).

Итог заранее одной строкой: **замер выполнен полностью, без демона и без
реального X11-ввода**, но дался не бесплатно — пришлось патчить путь к
hunspell-словарю (в системе он не установлен и sudo недоступен) и добавить
in-process bench-хук, вызывающий приватную decision-функцию демона напрямую.
Все цифры ниже — реальный прогон, не оценка на глаз.

## 1. Как именно запускался замер

### 1.1 Клонирование и разбор кода

```bash
git clone https://github.com/HelpFreedom/lay-x11 \
  /tmp/.../scratchpad/lay-x11
```

Изучены `README.md`, `HOW_IT_WORKS.md`, весь `src/`. Ключевой вывод по
архитектуре: **обычный CLI (`lay`) вообще не принимает решение
KEEP/CONVERT** — `src/main.rs` детерминированно вызывает
`dict::detect_direction()` (просто считает, каких символов больше,
кириллицы или латиницы) и **всегда** конвертирует. Это не то, что нужно
измерять как «автоопределение».

Настоящее автоопределение — фича `typing_assist` + `auto_switch_layout`
демона (`lay-daemon`), которая проверяет последнее набранное слово **после
пробела** и решает, чинить или нет. Реализована в одном private-модуле
`src/bin/lay_daemon.rs` (7100+ строк) функцией:

```rust
fn apply_typing_assist(text: &str, allow_layout_auto: bool) -> Option<String>
```

`None` = решение KEEP, `Some(text)` = решение CONVERT (с текстом-результатом).
Вызывается из `handle_typing_assist_after_space` для последних 1–2 «слов»,
собранных из evdev-событий — т.е. чистая текстовая функция, не завязанная на
реальный ввод. Это и есть предмет измерения.

Важный нюанс, который стоит знать до чтения метрик: **сама фича по
умолчанию выключена**. `LayConfig::default()` ставит `typing_assist: false`,
`auto_switch_layout: true`, но обе величины реально читаются только через
`active_typing_assist()/active_auto_switch_layout()`, которые в этом форке
управляются НЕ конфигом, а рантайм-тумблером `AUTO_OVERRIDE`
(переключается жестом Shift→Ctrl→Shift→Shift, сбрасывается при рестарте
демона). То есть из коробки, сразу после `install.sh` и ребута, демон **не
делает никакого автоисправления** — пользователь должен явно включить режим
жестом. Наш замер тестирует «потолок» алгоритма (жест включён,
`allow_layout_auto = true`), то есть даёт конкуренту максимально
благоприятные условия.

### 1.2 Сборка

```bash
cd scratchpad/lay-x11
cargo build --release        # обычная сборка — успех
cargo build --release --bin lay-daemon   # после патчей — тоже успех
```

Никаких отсутствующих X11-библиотек не потребовалось: раскладка
переключается через `x11rb` (pure Rust, XCB-протокол), без `libX11-dev`/
`libxkbcommon-dev` и т.п. Сборка прошла с первого раза на этой машине.

### 1.3 Проблема №1: hunspell-ru отсутствует, sudo недоступен

Вся словарная часть decision-логики (`russian_dictionary()`,
`russian_short_dictionary()`, `russian_tiny_dictionary()`,
`russian_generated_form_dictionary()`, а также RU n-gram модель в
`src/ngram.rs`) жёстко читает `/usr/share/hunspell/ru_RU.dic` /
`ru_RU.aff`. На этой машине установлен только `hunspell-en-us`, пакета
`hunspell-ru` нет, а по правилам задачи **устанавливать пакеты через sudo
нельзя**.

Без словаря все Russian-словари были бы пустыми — тогда ключевая функция
`correct_wrong_layout_ascii_word` (тот самый «ghbdtn → привет») никогда не
сработала бы вообще, и замер измерял бы не алгоритм, а отсутствие
зависимости. Чтобы получить честный результат (тот, что получил бы
пользователь, реально выполнивший `sudo apt install hunspell-ru` из
README), словарь был получен без sudo и без изменения системы:

```bash
apt-get download hunspell-ru        # только скачивание .deb из штатного
                                     # репозитория Ubuntu, без установки
dpkg-deb -x hunspell-ru_*.deb extracted   # распаковка архива в свою папку
```

Файлы `ru_RU.dic` (146 269 словарных статей) и `ru_RU.aff` скопированы в
`scratchpad/hunspell-local/`. В локальном клоне (только в нём, не в
системе) константы путей заменены на этот путь:

- `src/ngram.rs`: `RU_HUNSPELL`
- `src/bin/lay_daemon.rs`: добавлены константы `RU_HUNSPELL_DIC_PATH` /
  `RU_HUNSPELL_AFF_PATH`, подставлены в 5 мест, где раньше был литерал
  `"/usr/share/hunspell/ru_RU.dic"` / `"...aff"`.

Это единственное изменение поведения — оно не облегчает и не усложняет
алгоритм, а лишь подключает ту же самую словарную базу, которую
предполагает README.

### 1.4 Проблема №2: как прогнать корпус без демона и без X11

В `src/bin/lay_daemon.rs` добавлен bench-хук (вариант «б» из задания —
не трогать видимость функций, а дёрнуть их изнутри того же бинаря):

```rust
// добавлено перед стартом evdev/X11-инициализации в main()
if args[1] == "--bench-corpus" {
    run_corpus_bench(in_path, out_path)?;
    return Ok(());
}
```

`run_corpus_bench` читает TSV, для каждой строки вызывает
`apply_typing_assist(&input, true)` напрямую (без evdev, без uinput, без
X11-дисплея, без демона) и пишет предсказание. **Никакая клавиатура не
перехватывается, ни один демон не запускался.**

Запуск:

```bash
# конфиг «как после install.sh»: examples/config/{no_replace.example.txt,
# replacements.example.json} скопированы в $HOME/.config/lay/*, потому что
# именно так делает install.sh при первой установке — это честная базовая
# линия, а не искусственное послабление или ужесточение
HOME=scratchpad/fake_home \
  ./target/release/lay-daemon --bench-corpus \
  "docs/research/corpus/golden.tsv" \
  scratchpad/predictions-lay-x11.tsv
```

Результат: `[bench] processed 2300 rows`. Сырые предсказания лежат в
`docs/research/corpus/predictions-lay-x11.tsv` (колонки корпуса +
`predicted`, `predicted_text`, `verdict_match`).

Колонка `context` из корпуса **сознательно не передавалась** в
`apply_typing_assist` — потому что передавать её некуда. Сигнатура функции
`fn apply_typing_assist(text: &str, allow_layout_auto: bool) -> Option<String>`
не принимает предыдущий контекст вообще; в самом `lay-daemon` «предыдущее
слово» используется только как часть буфера, который целиком прогоняется
через ту же функцию как двухсловная фраза (для попытки починить разрыв
слова между собой), а не как отдельный сигнал для дизамбигуации текущего
слова («предыдущее слово было явно английским → значит и это, скорее
всего, английское»). Другими словами: у lay-x11 в принципе нет механизма
использовать контекст предложения для решения по короткому слову — это
не недостаток нашей тестовой обвязки, это факт архитектуры инструмента,
подтверждённый чтением кода. Прогон на голом `input` максимально точно
отражает его реальное поведение.

Корпус появился не сразу (готовился параллельно другим агентом) — ждали
опросом файла раз в ~2 минуты, нашёлся на второй итерации (~4 минуты
ожидания). Первый пробный прогон случайно попал в момент, когда файл ещё
дописывался: `wc -l` в тот момент показывал 2298 обработанных строк вместо
итоговых 2300, при том, что размер файла между двумя проверками не менялся
(совпадение по байтам при незавершённой записи). Это было замечено при
сверке с `validate.py` (эталонный валидатор корпуса, лежит рядом с
`golden.tsv`), который однозначно показал 2300 строк и `OK: all checks
passed`. Прогон был **выброшен и повторён** после проверки, что хэш файла
не меняется в течение 15 секунд подряд. Все цифры и файл `predictions-lay-x11.tsv`
ниже — из повторного, финального прогона на подтверждённо стабильных 2300
строках, все 12 категорий.

## 2. Метрики

Двоичное решение: `apply_typing_assist(input, true) == None` → предсказание
KEEP, `Some(_)` → CONVERT.

| Метрика | Значение |
|---|---|
| Всего примеров | 2300 |
| **Accuracy (общая)** | **85.9%** (1975/2300) |
| Ложные срабатывания (expect KEEP → got CONVERT) | **21** из 1705 KEEP-примеров = **1.2%** |
| Пропуски (expect CONVERT → got KEEP) | **304** из 595 CONVERT-примеров = **51.1%** |
| Precision по классу CONVERT | 93.3% (291 из 312 предсказанных CONVERT — верные) |
| Recall по классу CONVERT | 48.9% (291 из 595 нужных конвертаций — найдены) |

## 3. Разбор характерных ошибок (с точной причиной в коде)

Все 304 пропуска и 21 ложное срабатывание были прослежены до конкретной
причины в `src/bin/lay_daemon.rs` — ни одна не является «шумом».

### 3.1 [Главная проблема] Автоопределение работает только в одну сторону

`apply_typing_assist` вызывает `correct_wrong_layout_ascii_word` (строка
~2733) **только** для ASCII-токенов, и только конвертирует
US→RU (`Direction::Us2Ru`). Симметричной функции «кириллица набрана вместо
латиницы → перевести RU→US» **в авто-пути не существует**: остальные
кандидаты в цепочке (`correct_cyrillic_word_case`, `correct_hard_sign_typo`,
`correct_adjacent_transposition`, `correct_vowel_confusion`,
`correct_missing_letter` и др.) чинят опечатки **внутри** кириллицы, а не
меняют раскладку с RU на EN.

Следствие — категория `prose_en` (английский текст, набранный в русской
раскладке, например `ыщдв` → `sold`) пропускается почти полностью: 194 из
250 нужных конвертаций (**77.6% miss rate** внутри категории). Примеры
пропусков: `цфшеук`→`waiter`, `удузрфте`→`elephant`, `здфнштп`→`playing`,
`фдпщкшерь`→`algorithm` — все они синтаксически ничем не хуже примеров,
которые тот же алгоритм ловит в обратном направлении (`ghbdtn`→`привет`
конвертируется прекрасно). Это не единичный баг, а структурный пробел:
Ru→Us есть только в узкой функции `correct_wrong_layout_ascii_technical_token`
(только дефисные технические токены) и в отдельном manual-flow
double-Shift (`decide_completed_scope_word`), который требует явного
действия пользователя, а не «авто».

### 3.2 [Короткие слова] Однобуквенные слова технически не могут распознаваться

Категория `short1` (`f`→`а`, `,`→`б`, `d`→`в`, `;`→`ж`, `'`→`э` и т.д.) —
45 пропусков из 45 нужных конвертаций там, где ожидание CONVERT: **0%
recall**. Причина — не эвристика, а жёсткий фильтр длины: словари грузятся
через `load_hunspell_words_min_len(path, min_chars)`, и даже
`russian_tiny_dictionary()` использует `min_chars = 2`. Однобуквенные слова
(`а`, `и`, `в`, `к`, `с`, `у`, `я`, `о`, `ю`) **физически исключены** из
словаря на этапе загрузки — значит `is_known_russian_layout_autoswitch_word`
никогда не вернёт true для длины 1, и однобуквенные ошибки раскладки
принципиально не могут быть найдены этим путём, сколько угодно улучшай
остальную логику.

### 3.3 [Пунктуация как буква] Крайние `,` `;` `'` обрубаются до word-детекции

Русские клавиши `,` `;` `'` соответствуют латинским `б` `ж` `э`. Когда
такое письмо оказывается на границе токена (например `le,` = `дуб`, или
`,jznmcz` = `бояться`), `split_word_punctuation` (строка ~4010) отрезает
краевые символы по критерию `is_alphanumeric()`, не зная, что `,`/`;`/`'` в
контексте раскладки — это буква, а не пунктуация. В `apply_typing_assist`
это обрезание происходит **до** вызова `correct_wrong_layout_ascii_word`, и
усечённое слово (`le` вместо `le,`) уже не совпадает со словарной формой.
Затронуты все слова, начинающиеся/заканчивающиеся на б/ж/э — это заметная
доля обычной русской речи (`борщ`, `бегать`, `жасмин`, `хорошо`... часть
`хорошо` не задета, но `,jho`=`борщ` задета). Вносит основной вклад в 36
пропусков `prose_ru` и часть пропусков `short2` (`f;`→`аж`, `t\``→`её`).

### 3.4 [Морфология] Наивный suffix-stripping не покрывает словоформы

Оставшиеся пропуски `prose_ru` (без edge-punctuation бага) — словоформы,
которых нет буквально в hunspell-словаре как отдельная статья
(`работой`, `людям`, `делу`, `дерюга`→`lth.uf`), а
`is_known_russian_suffix_form`/`is_known_russian_verb_form`
(строки ~3504–3560) — это жёстко прописанный список окончаний с проверкой
«голой основы» в словаре, а не настоящий hunspell affix-анализ. Основа
типа `работ` (от `работой`) сама по себе не является словарной статьёй
(словарная форма — `работа`), поэтому проверка проваливается. Это
отдельный, более мелкий источник пропусков (порядка 10 из 36 в prose_ru).

### 3.5 [Ложные срабатывания] Точный словарь брендов не учитывает контекст

`~/.config/lay/replacements.json` (копия из `install.sh`) содержит точные
пары вида `"apple": "Apple"`, которые применяются **всегда**, включая
случаи, когда `apple` — не название компании, а обычное слово в тексте.
Пример: `apple` → `Apple` (id=869, ожидалось KEEP). Похожая динамика видна
и в самих эвристиках опечаток: `конечно`→`кончено`, `красиво`→`криво`,
`деньгам`→`деньга` — уже совершенно правильные русские слова были «исправлены»
в другое (тоже существующее) слово эвристиками
`correct_missing_letter`/`correct_vowel_confusion`, потому что n-gram
scorer посчитал вариант чуть более вероятным. Это самый дорогой тип ошибки
(правка того, что не было ошибкой), и здесь он не единичный: 3 таких
случая в `prose_ru`.

### 3.6 [Короткие слова] Двусмысленные 2-буквенные англо-русские омографы

12 ложных срабатываний в `short2`: `at`→`фе`, `if`→`ша`, `in`→`шт`,
`ye`→`ну`, `kb`→`ли`, `yj`→`но`, `tv`→`ем`, `jn`→`от`, `dj`→`во`, `gj`→`по`,
`nt`→`те`, `fq`→`ай`. Все эти латинские 2-буквенные токены после US→RU конвертации
попадают в короткий/крошечный словарь (тот же файл, `min_chars` 2–3) как
валидные русские частицы/предлоги/слова, и `allow_short_layout_word`
(≤3 латинских буквы + попадание в `russian_tiny_dictionary`) пропускает их
без дополнительной проверки контекста. Разрешить это без контекста фразы
(которого у функции просто нет — она видит только 1–2 «слова») практически
невозможно: `in`/`at`/`if`/`by` — частотные английские служебные слова,
которые он же уверенно ошибочно переклассифицирует как русские.

### 3.7 [Числа/аббревиатуры с дефисом] Ложное срабатывание на легитимные обозначения

4 ложных срабатывания в `number`: `ГОСТ-2024`→`UJCN-2024`, `Т-34`→`N-34`,
`Ту-154`→`Ne-154`, `АК-47`→`FR-47`. Причина —
`correct_wrong_layout_ascii_technical_token` (строка ~2885): она специально
ищет «кириллица + дефис + цифры без пробелов» как признак «пользователь
хотел набрать технический идентификатор в латинице» и конвертирует весь
токен RU→US. Эвристика не отличает реальный технический ID
(`фывa-123` → `asdf-123`) от легитимного русского обозначения с дефисом
и числом (советские индексы техники, номера ГОСТов) — которых в русском
языке довольно много.

## 4. Сильные стороны алгоритма

- **Очень низкий уровень ложных срабатываний там, где это важнее всего**:
  0/292 на `password`, `code`, `url`, `translit`, `abbrev`, `name` — то есть
  явная защита паролей, команд, URL и транслита сработала (частично за счёт
  `no_replace.txt`, частично за счёт того, что такие токены просто не
  попадают под словарные проверки).
- **Быстрая, детерминированная, не требует сети/LLM** — decision-функция
  работает на чистых строковых эвристиках + локальном hunspell-словаре;
  на этой сборке LLM-арбитр — заглушка (`src/llm.rs`, всегда `Ok(None)`),
  то есть весь результат получен именно эвристиками/словарём, без внешней
  модели.
- Отдельный `no_replace.txt` с ~200 предустановленными командами
  (`cd`, `git`, `docker`, языковые тулчейны и т.д.) реально защищает от
  порчи команд терминала — без него `cd` конвертировался бы в `св`.

## 5. Слабые стороны (по значимости для решения о разработке)

1. **Recall по CONVERT — 48.9%.** Больше половины нужных исправлений
   алгоритм просто не находит (пропуск = молчание, а не порча текста, но
   для «Punto-style» продукта это ключевая метрика ценности).
2. **Асимметрия направлений (п. 3.1)** — структурная, не мелочь: целая
   категория задач (EN-текст в RU-раскладке) не покрыта авто-режимом
   вообще. Это половина работы продукта, которой нет.
3. **Однобуквенные слова принципиально не распознаются** (п. 3.2) —
   `short1` категория безнадёжна при текущей архитектуре словарей.
4. **Фича по умолчанию выключена** (см. §1.1) — даже там, где алгоритм
   работает хорошо, обычный пользователь после `install.sh` и ребута его не
   получит без специального жеста Shift→Ctrl→Shift→Shift.
5. **Жёстко закодированная зависимость от системного пути хунспелла** и
   наивная (не affix-based) морфология — ограничивает recall на реальной
   прозе независимо от качества остальной логики.
6. Точечные, но показательные ложные срабатывания на брендовых словах
   (`apple`) и легитимных числовых обозначениях (`ГОСТ-2024`) — из-за
   отсутствия учёта контекста при точных словарных заменах.
