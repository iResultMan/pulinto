# Разведка: языковые модели и открытые данные для детекта «не та раскладка»

Дата: 2026-07-31.
Область: open-source аналог Punto Switcher для Linux. Нужна собственная (не-GPL) методология и данные для (а) детекта по завершённому слову и (б) инкрементального детекта по префиксу в 2–3 символа, при бюджете резидентного демона ≤6 МБ RSS.

Источник кода для анализа: `github.com/AndrewCrewKuznetsov/xneur-devel` (клонирован локально в
`/tmp/.../scratchpad/xneur-research/xneur-devel`, снят `--depth 1`, лицензия репозитория — GPL-2, поэтому сам код/данные напрямую использовать нельзя, но алгоритм как факт — можно).

## 1. Методология генерации proto/proto3 в xneur (разбор кода)

Файл генерации: `xneur/src/newlang_creation.c`, функции `generate()` и `generate_protos()`.
Ключ `xneur --generate`: «Generate proto and proto3 files from layout and sample text files» — берёт пробный текстовый файл `new/new.text` и раскладку и порождает `new/proto`, `new/proto3`.

Алгоритм (дословно из кода, с номерами строк):

1. **Перебор по клавишам, а не по буквам алфавита.** Внешний цикл идёт по кодам клавиш `i = 0..99` (`newlang_creation.c:131`), для каждого запрашивается символ на раскладке в двух состояниях модификатора — без шифта и с шифтом (`generate(..., 0)` и `generate(..., 1 << 7)`, строки 135–136). То есть база — «что физически можно напечатать на этой клавиатуре в этой раскладке», а не абстрактный алфавит языка.
2. **Фильтр `need_skip`** (строка 39–41): `isblank || iscntrl || isspace || ispunct || isdigit` — пробелы, пунктуация, цифры и управляющие символы исключаются из построения n-грамм. Границы слов отдельно не учитываются: пропускается сам символ-разделитель, но не проверяется, что n-грамма не пересекает границу слова — проверка присутствия делается через `strstr(text, buffer)` по всему файлу-корпусу целиком (строки 68, 89), т.е. если биграмма случайно встретилась на стыке двух слов в тексте, она будет засчитана как «существующая» и не попадёт в запрещённый список. Это не идеальная методология (у xneur нет предварительной токенизации по словам для этого шага).
3. **Порог частоты — бинарный, не частотный.** Никакого порога отсечения по частоте нет: используется чистое бинарное присутствие/отсутствие подстроки в тексте-корпусе через `strstr()` (строки 68, 89). Если биграмма `sym_i+sym_j` **не найдена** в тексте ни разу — она добавляется в `proto2` (список из 2 символов, файл `proto`) как «невозможная» (строка 70). Если биграмма встретилась (то есть допустима), для неё дополнительно перебираются все третьи символы `k` (ещё один цикл 0..99, строка 75) и по тому же принципу «строка не найдена в тексте» триграмма добавляется в `proto3` (строка 92).
4. **Регистр:** генерация работает с сырыми символами раскладки как есть; отдельного приведения к нижнему регистру в `generate()`/`generate_protos()` нет. Приведение регистра (`full_tolower()`, `xneur/lib/misc/text.c:92-103`) применяется только во время **распознавания** в рантайме (`detection.c`), не во время генерации словаря. `full_tolower` — не обычный `tolower()`: сначала ищет символ в таблицах `ch_up`/`ch_down` (нестандартные / диакритические соответствия), и только затем падает на `tolower()`. Отдельной обработки «ё» в просмотренном коде нет — `ё` обрабатывается как любая другая буква через общий алфавитный проход по клавишам.
5. **Формат хранения.** `proto2`/`proto3` — экземпляры `struct _list_char` (`xneur/lib/misc/list_char.c`) — это **отсортированный массив строк с бинарным поиском** (`get_add_id()`, строки 52–74 — классический binary search по `strcmp`), не дерево/trie/hash. Подтверждается тем, что файлы `proto`/`proto3` на диске отсортированы по алфавиту (проверено: `head ru/proto` → `аъ, аы, аь, бй, вй...`; `head ru/proto3` → `ааа, ааб, аав,...`).
6. **Числа подтверждены на диске** (репозиторий, `xneur/share/languages/`):
   - `ru/proto`: 203 строки, `ru/proto3`: 19141 строка;
   - `en/proto`: 69 строк, `en/proto3`: 8990 строк.
   Совпадает с цифрами из задачи — значит, актуальный апстрим не менялся.
7. **Рантайм-использование** (`xneur/lib/ai/detection.c`, порядок проверок в `check_lang()`, строки 365–429): сначала словарь (`get_dictionary_lang`), затем aspell/enchant спелл-чекер, затем эвристика по Левенштейну (`get_similar_words`, лимит `LEVENSHTEIN_LEN=3`), и только затем — как **последний резерв** — проверка запрещённых биграмм (`PROTO_LEN=2`) и следом триграмм (`BIG_PROTO_LEN=3`) методом скользящего окна по всему слову (`get_proto_hits()`, строка 166): если для текущей раскладки нашлась «запрещённая» n-грамма где-либо в слове, а для альтернативной раскладки — нет, слово признаётся набранным не в той раскладке. proto-эвристика в xneur — это подстраховка при отсутствии слова в словаре, а не основной метод.

**Вывод для собственной реализации:** методология xneur простая и грубая (бинарное присутствие/отсутствие, без частотного порога, без учёта границ слова при проверке), это создаёт шум (ложные «разрешения» из-за межсловных совпадений). У нас есть возможность сделать точнее: считать частоты n-грамм на количестве слов, а не «есть/нет в тексте», токенизировать корпус по словам явно и добавлять служебные символы начала/конца слова (как делают статистические языковые модели), и вводить частотный порог (например, n-грамма считается «невозможной для языка X», если её нет вообще ни в одном слове словаря/корпуса, а не просто «редко встречается»), сохраняя дух xneur, но с более чистым источником сигнала.

## 2. Инкрементальный детект по префиксу (2–3 символа)

### Требование
Пользователь набрал 2–3 символа; нужно решить «раскладка не та» до того, как слово закончено (`йцу` вместо `qwe`/аналог). Это существенно отличается от классификации целого слова: короткие последовательности несут мало сигнала, поэтому решение должно приниматься очень дёшево и с малой памятью, при этом допуская обновление оценки на каждый следующий символ (онлайн/потоково).

### Что используется в смежных задачах

- **Определение языка коротких строк (langid.py, CLD3, whatlang, lingua-py, fastText lid).** Все они по сути — n-граммные модели символов с наивным байесовским или логистическим классификатором поверх частот n-грамм. Ключевой практический вывод из литературы: **триграмм одного порядка недостаточно для очень коротких строк** — нужны n-граммы вперемешку размеров 1–5 (unigram..5-gram) с весами/backoff, иначе точность на коротких сегментах резко падает. Источник: обзор Besedo Engineering «Language Identification for very short texts» и сравнительные тесты langid/CLD3 на арХиве (ниже).
  - Бенчмарк: на коротких/маленьких датасетах langid.py показывает точность ~0.92, тогда как CLD3 — заметно хуже, ~0.73 (см. Jauhiainen et al., обзор точности систем LID; и отдельные сравнения langid vs CLD2/CLD3, где CLD3 «significantly weaker», langid/LanideNN/EquiLID стабильно >0.90). Для отдельных слов/очень коротких фраз langid-java даёт точность >80%. Прямых официальных цифр по срезу «1–5 символов» в проверенных источниках найти не удалось — это слепое пятно, отмечаем явно (не выдумываем цифру).
- **Марковские цепи по символам / character n-gram LM с backoff.** Классический подход (Cavnar & Trenkle 1994, «N-Gram-Based Text Categorization») — считать профиль частот n-грамм (символьных, порядка 1–5) для каждого языка/раскладки и сравнивать через out-of-place ранговую метрику или через простую вероятность цепи Маркова. Это дешевле по памяти, чем полноценные trie словарей, и хорошо ложится на потоковую обработку посимвольно (можно пересчитывать вероятность инкрементально: `P(w) = P(c1)·P(c2|c1)·P(c3|c1,c2)·...`, без re-scan всего слова).
- **Префиксные структуры (trie/DAWG/FST) для быстрой проверки «существует ли такой префикс в словаре языка X».** Практический бенчмарк (`marisa-trie`/`DAWG` для Python, документированный в блоге автора `kmike.ru` и в `marisa-trie` docs) на 3 млн русских слов:
  - `dict` (обычный питоновский dict строка→длина): ~600 МБ
  - `list` строк: ~300 МБ
  - `marisa_trie.RecordTrie`: ~11 МБ
  - `marisa_trie.Trie`: ~7 МБ
  - `dawg.DAWG`: ~2 МБ
  - `dawg.CompletionDAWG` (умеет "есть ли слова с таким префиксом" — ровно наша операция для инкрементального детекта): ~3 МБ
  - `dawg.IntDAWG`: ~2.7 МБ, `dawg.RecordDAWG`: ~4 МБ
  Источник: `marisa-trie` benchmarks (`marisa-trie.readthedocs.io/en/latest/benchmarks.html`, `github.com/pytries/marisa-trie/blob/master/docs/benchmarks.rst`) и `kmike.ru/python-data-structures/`.
- **Bloom-фильтры для словарей.** Исторически один из первых применений Bloom-фильтра — Unix `spell` (см. «How Unix Spell Ran in 64kB RAM», blog.codingconfessions.com) — хранение словаря английского языка в считанных десятках килобайт при заданном FPR. Практическое правило: ~10 бит/слово даёт FPR около 1% (пример из литературы: 100 000 слов, 1 024 000 бит ≈ 128 КБ, 5 хэш-функций → FPR ≈ 0.86%). Минус для нашей задачи: классический Bloom-фильтр отвечает только «слово целиком есть/нет», не «есть ли продолжение у префикса» — для префиксной проверки нужен либо отдельный фильтр по каждой длине префикса (дорого), либо counting/prefix-вариант, либо просто отдельный trie/DAWG.

### Практическая рекомендация под бюджет ≤6 МБ RSS демона

Комбинация из двух слоёв, а не одна структура на всё:

1. **Слой 1 — быстрое посимвольное решение (работает с 2-го/3-го символа), почти нулевая память.**
   Взять идею xneur (запрещённые биграммы/триграммы по раскладке), но хранить не список строк с бинарным поиском, а **битовую карту по алфавитному радиксу**. Для русского алфавита (33 буквы без Ё/Ё≈Е) число возможных триграмм — `33^3 = 35 937`, битовая карта — `35937/8 ≈ 4.5 КБ`; биграммы `33^2=1089` → 137 байт. Для английского (26 букв) триграммы `26^3=17 576` → ~2.2 КБ. Итого весь корпус запрещённых/разрешённых n-грамм для пары ru/en укладывается в **≤ 15–20 КБ**, на порядки меньше, чем строковый список xneur (который тоже мал по абсолютной величине — 19141 строк по 3-4 байта ≈ 60-80 КБ на диске, — но битовая карта быстрее: O(1) вместо O(log n) и без указателей/malloc на строку). Это даёт мгновенный (с 2–3 символов) сигнал «эта комбинация никогда не встречается в языке X», без обращения к словарю.
   Улучшение методологии по сравнению с xneur (см. раздел 1): не бинарное присутствие в сыром тексте, а частотный подсчёт по токенизированным словам с явными маркерами начала/конца слова (`^ci`, `cj$`), что убирает шум от межсловных склеек и даёт возможность держать порог (например, «встречается менее чем в N словах словаря» → считать запрещённой) вместо жёсткого «встречалась хоть раз».
2. **Слой 2 — подтверждение по словарю после 4+ символов / на границе слова.**
   `dawg.CompletionDAWG` (или аналог на Rust/C, например `fst` crate от BurntSushi, тоже DAWG/FST-based, обычно в том же порядке величин) на топ-частотных словах языка даёт операцию «есть ли слова с таким префиксом» за время O(длина префикса), при памяти около 2–4 МБ на 1–3 млн словоформ (см. цифры выше). Для бюджета 6 МБ на **весь** демон нецелесообразно тащить полный словарь словоформ (это уже съест почти весь бюджет на одну структуру, без учёта рантайма Rust/C, X11-хуков и т.д.). Практичнее — **урезанный словарь** (топ 30 000–100 000 самых частотных словоформ на язык, не лемм) в виде DAWG/FST: по грубой экстраполяции таблицы marisa-trie (2–3 МБ на 3 млн слов, то есть ~1 байт/слово в DAWG-представлении) — 100 000 слов уместятся в раойне **100–300 КБ на язык**, то есть обе структуры (ru+en) — точно меньше 1 МБ. Это оставляет запас в бюджете 6 МБ на код, стек, X11/XKB-состояние демона.
   Если DAWG/FST-библиотеку тащить не хочется (лишняя зависимость на C/Rust), fallback — Bloom-фильтр только для полных слов (10 бит/слово, см. выше), который решает вопрос «это точно не слово этого языка» дешевле, но не даёт префиксной семантики — годится только как последняя проверка на границе слова, не для инкремента посимвольно.
3. Итоговая архитектура: **Слой 1 (битовые карты запрещённых n-грамм) — с первого 2–3-го символа → Слой 2 (мини-DAWG топ-слов) — при завершении слова / пробеле, для более уверенной коррекции и для построения списка «отменить автозамену».** Оценка суммарной памяти под данные: **≤ 1 МБ на пару языков ru+en**, что оставляет пятикратный запас в бюджете 6 МБ RSS на код рантайма, X11/evdev-хуки, буферы и т.п.

## 4. Размер данных и достижимая точность

- **Порядок величины словаря словоформ.** Для полноценного словаря русского языка (все словоформы, не леммы) типичный размер — от нескольких сотен тысяч до нескольких миллионов записей (пример: benchmark marisa-trie/DAWG выше явно оперирует «3 млн русских слов» как реалистичным полным словарём словоформ). Для целей эвристики «эта комбинация букв нехарактерна для языка» достаточно значительно меньше — топ 30–100 тыс. самых частотных словоформ покрывает подавляющее большинство обычного бытового набора текста (степенной закон Ципфа: относительно небольшое ядро словаря даёт основную долю встречаемости в тексте).
- **N-граммы.** xneur обходится 203 биграммами и ~19 тыс. триграммами для русского при бинарном подходе «есть/нет в тексте» — это уже рабочий бюджет, наша более чистая (частотная, с границами слов) методология даст сопоставимый или меньший по объёму список (за счёт устранения шумовых «разрешений» от межсловных склеек список запрещённых комбинаций скорее увеличится по факту, но представление в виде битовой карты по алфавитному радиксу делает абсолютный размер несущественным — весь диапазон n-грамм заранее ограничен `33^3`/`26^3`).
- **Точность на коротких строках — предметная область есть, но с оговоркой.** Прямых, проверенных на официальных страницах количественных цифр вида «точность X% на строках длиной 1–5 символов» найти не удалось (это отдельное белое пятно, отмечаем явно, а не подставляем недостоверное число). Косвенные, но проверяемые ориентиры из литературы:
  - Устоявшийся вывод в LID-литературе (обзор Besedo Engineering «Language Identification for very short texts», сравнения langid/CLD2/CLD3): при переходе от длинных документов к коротким фразам/словам точность классических триграммных LID-моделей заметно падает, и решение — смешивать n-граммы разных порядков (1–5), а не полагаться на один порядок.
  - На «маленьких» (коротких) выборках langid.py показывает ~0.92 точности против ~0.73 у CLD3 (сравнительные тесты цитируются в обзорных работах по LID, напр. в связи с Jauhiainen et al. и последующими сравнениями langid/CLD2/CLD3/LanideNN/EquiLID, где последние три стабильно >0.90, а CLD3 «значительно слабее»).
  - Для отдельных слов/очень коротких фраз langid-java даёт точность «более 80% тестовых случаев» — единственная цифра, которая явно привязана к сегменту «отдельное слово», а не «документ».
  - **Практический вывод для нашей задачи проще**, чем общий LID: мы не различаем «какой из 100 языков», а различаем «раскладка A или раскладка B» при известном отображении клавиш — это гораздо более узкая и разрешимая подзадача, чем общий LID, поэтому даже примитивная битовая карта запрещённых n-грамм (методология xneur, уточнённая в разделе 1) даёт практически применимый результат уже на проде xneur/Punto много лет — ориентируемся на неё как эмпирическое подтверждение работоспособности подхода, а не на абстрактные цифры точности LID-бенчмарков, которые решают другую задачу.

## Рекомендуемый план получения собственных данных

1. **Собрать корпуса-источники (все под свободными лицензиями, без Ляшевская-Шаров/Kelly и без Mystem):**
   - Wikipedia dumps `ruwiki-latest-pages-articles.xml.bz2` и `enwiki-latest-pages-articles.xml.bz2` — `dumps.wikimedia.org` (GFDL + CC BY-SA 4.0).
   - Wiktionary dumps `ruwiktionary`/`enwiktionary` — тот же `dumps.wikimedia.org`, либо готовый JSONL-экстракт с `kaikki.org` (та же лицензия GFDL/CC BY-SA 4.0, унаследованная от источника).
   - OpenCorpora XML-словарь словоформ — с opencorpora.org (когда сайт снова доступен; на 31.07.2026 отдаёт 522) — CC BY-SA.
   - Hunspell `ru_RU`/`en_*` из `github.com/LibreOffice/dictionaries` — BSD-3-Clause / (для английских словарей Hunspell отдельно проверить README, обычно тоже пермиссивные лицензии).
   - Leipzig Corpora Collection, разделы Russian/English (`wortschatz.uni-leipzig.de/en/download/...`) — CC BY 4.0, готовые частотные списки слов и n-gram co-occurrence — использовать как основной источник частот и как перекрёстную проверку.
   - OpenSubtitles через OPUS (`opus.nlpl.eu`, зеркало на Hugging Face `Helsinki-NLP/OpenSubtitles2024`) — ODC-BY — для бытовой/разговорной лексики и коротких слов/междометий.
   - АОТ (aot.ru) словари — LGPL — как дополнительный/сверочный источник словоформ для русского.
2. **Нормализация:** привести все источники к единой токенизации (по словам, с явными маркерами `^`/`$` начала/конца слова), привести регистр через explicit lowercasing с корректной обработкой `ё`→`е` только там, где это осознанно нужно для частотного анализа (решить отдельно, схлопывать ли ё/е — в отличие от xneur, где это не обрабатывалось явно, можно сделать осознанный выбор и задокументировать его).
3. **Подсчёт частот n-грамм (би-, три-, при необходимости тетраграммы) раздельно по языку**, с порогом отсечения (например, n-грамма считается «непринадлежащей языку X», если частота ниже порога `ε` по всему объединённому корпусу) — воспроизводит идею xneur, но убирает бинарный шум и добавляет управляемый порог.
4. **Построение слоя 1** — битовая карта разрешённых/запрещённых n-грамм по алфавитному радиксу для пар раскладок (ru/en в первую очередь), размер ≤20 КБ.
5. **Построение слоя 2** — DAWG/FST (или, как минимум затратный по разработке fallback, Bloom-фильтр для полных слов) на топ 30–100 тыс. словоформ на язык, из объединения OpenCorpora + Hunspell + Leipzig top-frequency, размер ориентировочно ≤1 МБ суммарно на оба языка.
6. **Лицензирование итогового датасета:** поскольку в состав входят CC BY-SA источники (OpenCorpora, Wiktionary/Wikipedia) с обязательством share-alike, готовый производный датасет n-грамм/словарей стоит выпускать под **CC BY-SA** (или более открытой, если полностью отказаться от share-alike-источников и остаться только на CC BY / BSD / LGPL источниках — тогда возможен CC BY или даже public domain для самих числовых списков частот, но это нужно решить осознанно на этапе релиза, а не постфактум).
7. **Валидация:** прогнать построенный слой 1+2 на отложенной выборке реальных «случайно набранных не в той раскладке» слов (можно сгенерировать синтетически — взять словарь одного языка и применить обратное отображение клавиш другого) и замерить precision/recall по решению «переключать/не переключать» отдельно на префиксах длины 2, 3, 4+ символа — так как готовых внешних бенчмарков именно под эту узкую задачу не найдено (см. раздел 4), собственная валидация обязательна перед релизом.
