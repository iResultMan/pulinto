# Разведка: перехват клавиатурного ввода в Linux и проблема Enter

Дата: 2026-07-31. Метод: чтение исходников (клонирование репозиториев там, где возможно), README/issue-трекеры/спецификации протоколов. Блоги использованы только как вторичное подтверждение фактов, уже видных в первоисточниках. Везде, где утверждение не подтверждено первоисточником, это помечено явно.

## 1. Перехват с возможностью задержки: `EVIOCGRAB` + `/dev/uinput`

### 1.1 Принцип

`EVIOCGRAB` — ioctl на файловом дескрипторе `/dev/input/eventN`. При вызове с аргументом `1` устройство переходит в режим **эксклюзивного захвата**: события с этого устройства продолжают попадать *в ядро* и *в грабящий процесс*, но перестают доставляться любым другим читателям того же evdev-узла (X-серверу, libinput, другим демонам). Это даёт ровно то, что нужно: процесс получает событие первым и *единолично*, может подумать над ним сколько нужно (в разумных пределах) и either переслать его как есть, either не пересылать вовсе, заменив собственной последовательностью через `/dev/uinput` (виртуальную клавиатуру).

Это подтверждено многократно в LKML-обсуждениях семантики `EVIOCGRAB`: «EVIOCGRAB is an ioctl on an evdev device which causes all events to go to that handler, and that client, exclusively. While this grab is active, other processes will not receive events from the kernel devices» — [LKML: input: evdev.c EVIOCGRAB semantics question](https://linux-kernel.vger.kernel.narkive.com/UBtQOowI/input-evdev-c-eviocgrab-semantics-question).

### 1.2 Кто так делает — обзор реальных проектов

| Проект | Архитектура | Источник |
|---|---|---|
| **keyd** (`rvaiya/keyd`) | Системный демон, `evdev` (грабит) + `uinput` (виртуальная клавиатура). Заявленная задержка обработки — «hand tuned input loop written in C that takes ≪1ms» | [README, rvaiya/keyd](https://github.com/rvaiya/keyd) |
| **interception-tools** (GitLab `interception/linux/tools`) | Разделён на 4 бинарника: `intercept` (грабит устройство, пишет события в stdout), `uinput` (создаёт виртуальное устройство, читает stdin), `udevmon` (по udev-правилам запускает пары `intercept → <плагин-фильтр> → uinput` в конвейер). Явное разделение «захват / решение / инъекция» на разные процессы, связанные пайпом | найдено через ArchWiki и вторичные описания архитектуры; официальный README на момент разведки не открылся напрямую (404 при прямом запросе raw-файла) — **зафиксировать как не проверено по первоисточнику**, только по независимым описаниям (ArchWiki, GitLab-дерево репозитория) |
| **kmonad** | Аналогично: `ioctl`-грабит указанный `device-file` (рекомендуется `/dev/input/by-id/...`, т.к. имя в `/dev/input/eventN` не стабильно при переподключении) | [kmonad README/issue #1010](https://github.com/kmonad/kmonad/issues/1010) |
| **xremap** | Явно заявляет: «Xremap uses evdev and uinput, which works whether you use X11 or Wayland» — то есть на Wayland тоже работает через тот же evdev/uinput слой, а не через Wayland-протоколы | [xremap/xremap README](https://github.com/xremap/xremap) |
| **evremap** (`wez/evremap`) | «grabbing exclusive access to an input device and maintaining a model of the keys that are pressed», эмиссия в виртуальное устройство. Работает «at the evdev layer of libinput» — то есть ниже X11/Wayland, системно-универсально (X11, Wayland, голая консоль) | [wez/evremap README](https://github.com/wez/evremap) |

Общий паттерн у всех пяти: **грабим устройство → держим состояние клавиш в памяти процесса → синтезируем корректный поток в `uinput`**. Это ровно модель, нужная для отложенного решения по Enter: событие Enter можно на долю секунды придержать в демоне, посмотреть, не является ли предыдущее слово ошибочным по раскладке, и либо отпустить Enter как есть, либо сначала впрыснуть Backspace-ы и новое слово, а потом Enter.

**«Tapper»** — в задаче упомянут как аналог; по результатам поиска на GitHub такого проекта под этим именем в контексте evdev/Linux-ремапперов найти не удалось (нашлись только несвязанные репозитории). Раздел проекта `delegated-hatching-allen.md` в этом же репозитории также упоминает «shift-shift» и «Tapper» как переключатели раскладки без конвертации текста — но это внутренняя заметка, не первоисточник; **факт о Tapper не подтверждён отдельным поиском и помечается как неподтверждённый**.

### 1.3 Реальная задержка

Единственная опубликованная в первоисточнике цифра — заявление keyd о «≪1 мс» на итерацию input loop ([README](https://github.com/rvaiya/keyd)). Для остальных проектов (interception-tools, kmonad, xremap, evremap) конкретных цифр latency в README/issue-трекерах в ходе разведки найдено не было — **не подтверждено**. Порядок величины стоит считать сопоставимым: один syscall `read()` на `/dev/input/eventN` + пользовательская логика (обычно микросекунды на сравнение строки-буфера со словарём) + один `write()` в `/dev/uinput`; на современном железе это заведомо меньше кадра видимости человеком (~16 мс), но нагрузка на диспетчер (планировщик ОС, приоритет процесса) может добавлять джиттер, если демон не realtime-приоритезирован — сами проекты этот аспект в документации не разбирают.

### 1.4 Что происходит при падении демона

Здесь два принципиально разных сценария, которые в найденных материалах не разделяются явно, но вытекают из семантики ядра:

1. **Процесс завершается (в том числе аварийно, SIGSEGV/panic).** Ядро закрывает все файловые дескрипторы упавшего процесса, в том числе дескриптор `/dev/input/eventN`, на котором держался граб. Освобождение граба при закрытии дескриптора — часть контракта `EVIOCGRAB`; это же явно чинили в ядре для смежного случая (переподключение/отключение устройства): «we need to release eventual grabs on the underlying input device as we also release the input device itself. Otherwise, we would try to release the grab when the client that requested it closes its handle, accessing the input device which might already be freed» — патч [«evdev: Release eventual input device grabs when getting disconnected»](https://lkml.iu.edu/hypermail/linux/kernel/0803.3/2709.html). Отсюда следует (и это стандартное поведение ядра для дескрипторов вообще): **при вылете процесса граб снимается автоматически**, клавиатура возвращается к нормальной работе без грабящего слоя — просто перестаёт работать ремаппинг/автозамена, сырые события снова видят X11/Wayland напрямую.
2. **Процесс жив, но завис или работает некорректно** (бесконечный цикл, дедлок, битый конфиг, который не приводит к падению). Дескриптор не закрывается — устройство остаётся эксклюзивно захваченным нерабочим процессом, и клавиатура эффективно «умирает» для всей остальной системы. Это принципиально более опасный сценарий, и именно под него авторы `keyd` встроили аппаратный (точнее, «в самом низкоуровневом коде демона, до применения любого маппинга») аварийный выход: «It is possible to render your machine unusable with a bad config file. Should you find yourself in this position, the special key sequence `backspace+escape+enter` should cause keyd to terminate» — [README, rvaiya/keyd](https://github.com/rvaiya/keyd). Это прямое признание разработчиков, что «зависший, но не упавший» граббер — реальный и заранее продуманный класс отказа, и единственный принятый в индустрии failsafe — жёстко прошитая аварийная комбинация, обрабатываемая раньше пользовательского конфига.

kmonad отдельно фиксировал смежный класс проблем — не зависание, а падение/некорректную обработку при *дисконнекте устройства* (например, KVM-переключатель отключает клавиатуру), для чего добавили `:ignore-missing` с ожиданием устройства через `inotify` вместо падения демона, и отдельно улучшили диагностику: «Show os error on ioctl grab/release failure on Linux» — [kmonad issue/PR #1017](https://github.com/kmonad/kmonad/issues/1017).

### 1.5 Несколько граббер-процессов одновременно

`EVIOCGRAB` — **строго эксклюзивный** захват: второй процесс, пытающийся грабить уже захваченное устройство, получает ошибку. Man-страница `evtest` описывает это через собственное поведение утилиты: «The grab is released again when evtest quits» — то есть пока держит один процесс, другой не может; это же constatируется в LKML-треде о семантике EVIOCGRAB, где обсуждается сама идея добавить неисключительные уровни грабов именно потому, что текущая семантика — только «всё или ничего» на один клиент — [LKML-тред](https://linux-kernel.vger.kernel.narkive.com/UBtQOowI/input-evdev-c-eviocgrab-semantics-question). Практическое следствие: **PuLinTo и, например, `keyd`/`kmonad`/любой другой ремаппер не могут одновременно грабить один и тот же физический `/dev/input/eventN`** — это подтверждено и вживую пользователями `easy-switcher`, у которого в README прямо написано: «It doesn't work correctly together with key remappers such as keyd and works better if you use single-key shortcut for layout switching» — [freemind001/easy-switcher README](https://github.com/freemind001/easy-switcher). Это прямое документированное подтверждение конфликта двух грабберов на одном устройстве от практикующего разработчика конкурирующего Linux-переключателя раскладки.

Обход конфликта, применяемый в экосистеме: `interception-tools` специально построен как *конвейер* (один процесс держит граб, остальные — чистые Unix-фильтры на stdin/stdout), чтобы несколько логических «модулей» (caps2esc, debouncer и т.д.) не конкурировали за сам граб, а работали над одним потоком последовательно.

## 2. Принципиальное ограничение X11: XRecord против XGrab*

### 2.1 XRecord — только наблюдение, подтверждено спецификацией

Спецификация протокола прямо разделяет два типа событий, которые может видеть RECORD-клиент:

> «Device events are events generated by core X devices or extension input devices that the server may or may not deliver to any clients. […] the recording of selected device events is not affected by server grabs» — [Record Extension Protocol Specification, X.Org](https://www.x.org/releases/X11R7.6/doc/recordproto/record.html)

Ключевое следствие: RECORD **копирует** событие для клиента-наблюдателя, но не имеет средства ни задержать, ни отменить его доставку целевому окну. Это именно то ограничение, которое сформулировано в задаче, и оно **подтверждается** первоисточником (спецификацией протокола), а не только вторичными блогами: XRecord — «sniffer», Enter, увиденный через XRecord, к моменту, когда демон о нём узнал, уже доставлен приложению. Задержать его в принципе нельзя.

### 2.2 Что в X11 действительно может задержать доставку — и какой ценой

`XGrabKeyboard` / `XGrabKey` — активный грабинг на уровне X-протокола: события клавиатуры перестают доставляться исходному клиенту (окну) и идут только грабящему клиенту, который может решить, что с ними делать, и при необходимости воспроизвести их приложению через `XTestFakeKeyEvent` (расширение XTEST). Это структурно то же самое, что `EVIOCGRAB`+`uinput`, но на уровень выше — в X-сервере, а не в ядре.

**Прямое доказательство из живого проекта, а не из теории.** В исходниках `xneur` (репозиторий, который сейчас сопровождается сообществом на GitHub) обнаружен именно такой механизм:

```
xneur/lib/main/focus.c:232:
    XGrabKey(display, AnyKey, AnyModifier, window, FALSE, GrabModeAsync, GrabModeAsync);
```

— пассивный граб *абсолютно всех* клавиш (`AnyKey, AnyModifier`) на окне, которое в данный момент находится в фокусе (тот же файл отслеживает смену фокуса через `XSelectInput(display, window, FOCUS_CHANGE_MASK)` и перевешивает граб на новое окно при каждом переключении фокуса). Полученные так события затем воспроизводятся в реальное окно через `XTestFakeKeyEvent` (символ присутствует в том же `focus.c`). Источник: [AndrewCrewKuznetsov/xneur-devel, xneur/lib/main/focus.c](https://github.com/AndrewCrewKuznetsov/xneur-devel/blob/master/xneur/lib/main/focus.c) и [.../bind_table.c](https://github.com/AndrewCrewKuznetsov/xneur-devel/blob/master/xneur/lib/main/bind_table.c) (клон сделан напрямую в ходе этой разведки, `grep` по исходникам не находит ни одного использования `XRecord*` во всём дереве — так что расхожее «xneur работает через XRecord» для актуальной версии исходников **не подтверждается кодом**; xneur исторически именно «грабит всё + replay», а не «наблюдает через RECORD»).

Цена этого подхода, видная непосредственно из архитектуры:
- Грабится **всё** на фокусном окне — конфликтует с любым другим клиентом, который тоже пытается повесить свой `XGrabKey`/`XGrabKeyboard` на то же окно/дисплей (типичный конфликт — менеджеры окон, скринлокеры, другие глобальные хоткей-демоны); в X одновременный активный грабинг одного и того же события двумя клиентами невозможен так же, как и `EVIOCGRAB` — по той же логике «одна доставка одному клиенту».
- Грабинг привязан к **конкретному окну** и должен перевешиваться при каждой смене фокуса (`FOCUS_CHANGE_MASK`) — в момент самого переключения есть окно гонки.
- Работает только в границах одного X-дисплея/сессии; не действует в TTY-консоли, не действует для не-X11-клиентов (чистый Wayland-клиент под XWayland обычно тоже не участвует в этом протоколе так же, как настоящее X11-приложение).
- Не переносится на Wayland в принципе — Wayland-протокол не имеет аналога `XGrabKeyboard`/`XTestFakeKeyEvent` для стороннего клиента (см. раздел 4).

Итог по разделу 2: в задаче сформулированное утверждение «XRecord может только наблюдать» **подтверждено спецификацией**; но из этого нельзя делать вывод «в X11 в принципе невозможно задержать Enter» — возможность есть (`XGrabKey`/`XGrabKeyboard` + `XTestFakeKeyEvent`), она реально используется существующим свободным переключателем раскладки (xneur), но обходится дороже, чем `EVIOCGRAB`+`uinput`, и по крайней мере не универсальнее его (работает только под X11/XWayland, а не под «голым» Wayland-композитором).

## 3. Как существующие переключатели обходятся с Enter

Вывод из просмотренных проектов: **никто не пытается «правильно предсказать» Enter в реальном времени через ту же логику, что и обычные буквы**. Везде используется один из двух паттернов: (а) Enter — триггер сброса буфера, а не триггер конвертации, либо (б) конвертация вообще не автоматическая, а по явному хоткею пользователя, так что гонка с Enter структурно невозможна.

### 3.1 xneur

Конфиг `xneurrc` (man-страница `xneurrc(5)`) содержит выделенные опции именно под этот случай:

- **`FlushBufferWhenPressEnter`** — «This option disable or enable flushing internal buffer when pressed Enter or Tab.»
- **`DontProcessWhenPressEnter`** — «This option disable or enable processing word when pressed Enter or Tab.»
- Отдельно — целая группа `Troubleshoot*` (`TroubleshootSwitch`, `TroubleshootBackspace`, `TroubleshootLeftArrow/RightArrow/UpArrow/DownArrow`, `TroubleshootDelete`) — включает/выключает автопереключение раскладки при нажатии соответствующих клавиш.

Источник: [xneurrc man page (Ubuntu manpages)](https://manpages.ubuntu.com/manpages/xenial/man5/xneurrc.5.html). Явной опции `TroubleshootEnter` в этом списке не встретилось — обработка Enter вынесена в отдельную пару опций (Flush/DontProcess), а не в общий Troubleshoot-список; **это стоит считать зафиксированным по документации, но не 100%-но исчерпывающим** — полный набор опций проверялся только по man-странице, не по исходному парсеру конфига.

### 3.2 xswitcher (`ds-voix/xswitcher`)

В `xswitcher.conf` Enter явно выведен из числа клавиш, которые продолжают накопление буфера для последующей конвертации:

```
NewSentence = [ "SEQ:(ENTER:0)" ]      # отпускание Enter — сброс буферов, "новое предложение"
Drop        = ["ESC", "TAB", "ENTER", "KPENTER", "LINEFEED..POWER"]
```

а сама конвертация слова (`Action.RetypeWord`) триггерится не автоматически и не Enter’ом, а отдельной явной комбинацией — `Pause` или правый `Ctrl` (`SEQ:(PAUSE:1,PAUSE:0)` / `SEQ:(R_CTRL:1,R_CTRL:0)`). Источник: [ds-voix/xswitcher, xswitcher.conf](https://github.com/ds-voix/xswitcher/blob/main/xswitcher.conf).

### 3.3 easy-switcher (`freemind001/easy-switcher`)

Полностью ручная модель: «Easy Switcher writes your keystrokes to internal buffer, and when you press a special key (Pause/Break by default), it erases what you have written, changes the layout, and writes the correct input back.» — автоконвертации в реальном времени по мере набора здесь вообще нет; пользователь сам решает, когда исправлять, поэтому конфликт «Enter уже отправил» структурно исключён — если пользователь уже нажал Enter, повторное нажатие Pause просто ничего разумного не сделает (буфер уже сброшен вводом), а не «выстрелит в новую строку». Источник: [freemind001/easy-switcher README](https://github.com/freemind001/easy-switcher).

### 3.4 Punto Switcher (Windows, закрытый код — только форумные и пользовательские источники)

Punto Switcher не имеет открытого кода, поэтому здесь допустимы только вторичные источники (форумы, блог самого Яндекса) — это ниже уровня достоверности, чем п. 3.1–3.3, и явно помечается как таковое.

- В настройках есть раздел «Проблемы совместимости» с опцией вида «не переключать раскладку, если до этого были нажаты определённые клавиши» — то есть штатный, документированный механизм подавления автозамены после конкретных клавиш существует, но прямого явного упоминания «Enter» как one of these специально под сценарий «уже отправлено сообщение» в найденных материалах нет — [список параметров, блог «Клуб Punto Switcher»](https://yandex.ru/blog/punto/isklyucheniya).
- Есть отдельный, независимый от Troubleshooting-настроек механизм — список программ-исключений («Программы-исключения»), и типовая рекомендация в комьюнити — вручную добавлять туда терминалы/консоли, чтобы Punto вообще не трогал в них раскладку — источники форумные, не официальная документация.
- Жалобы пользователей на порчу текста после автозамены в мессенджерах (в частности, веб-Telegram) встречаются на форумах, но конкретно жалоба «слово исправилось уже после Enter, второй строкой/вторым сообщением» как отдельно поименованный, обсуждаемый в тредах баг **не встретилась** в ходе этой разведки — **не подтверждено**, вероятно потому что Punto достаточно старый и «залатанный» продукт, где этот конкретный класс багов, видимо, был закрыт эвристиками задолго до текущих форумных обсуждений.

### 3.5 Caramba Switcher

Проект закрытый (Windows-shareware/freeware), исходников нет. В ходе поиска не нашлось ни официального репозитория, ни специфичного обсуждения обработки Enter — **не подтверждено, источников нет**. Единственные найденные упоминания — общее описание функциональности («automatically corrects keyboard layout») без деталей триггеров.

### 3.6 Вывод раздела 3

Все проверяемые по исходникам/документации Linux-инструменты (xneur, xswitcher, easy-switcher) **сознательно не пытаются автоматически исправлять слово по факту нажатия Enter** — либо Enter явно сбрасывает буфер без исправления (xneur, xswitcher), либо исправление вообще не автоматическое, а по ручному хоткею (easy-switcher). Ни один из просмотренных проектов не описывает «умную» логику вида «мы уже увидели Enter, но всё равно решили пере-набрать строку заново». Это сильный сигнал в пользу консервативной архитектуры для PuLinTo (см. раздел 6).

## 4. Wayland: легальные пути перехвата/синтеза ввода в 2026 году

### 4.1 Протоколы синтеза ввода и их реальная поддержка композиторами

| Механизм | Что делает | Поддержка на 2026 |
|---|---|---|
| **`virtual-keyboard-unstable-v1`** | Клиент просит композитор сымитировать нажатия «настоящей» клавиатуры | Поддерживают: sway, Hyprland, COSMIC, niri, labwc, Mir и др. — [wayland.app protocol page / вторичные источники]. **Не поддерживают: mutter (GNOME)** — открытые задачи в трекере GNOME, [work item #4124 «Implement virtual-keyboard-v1 protocol»](https://gitlab.gnome.org/GNOME/mutter/-/work_items/4124) и [#1974](https://gitlab.gnome.org/GNOME/mutter/-/work_items/1974) до сих пор открыты; **и KWin (KDE)** — открытые баги [#497774](https://www.mail-archive.com/kde-bugs-dist@kde.org/msg1046385.html), [#502882](https://www.mail-archive.com/kde-bugs-dist@kde.org/msg1046107.html), [#512996 «KWin lacks virtual-keyboard-unstable-v1 protocol»](http://www.mail-archive.com/kde-bugs-dist@kde.org/msg1118727.html) |
| **`input-method-unstable-v2`** | Протокол для IME (композиция CJK-текста, pre-edit) поверх аппаратной клавиатуры | Тестировался на sway; распространяется на тот же узкий круг wlroots-совместимых композиторов, что и virtual-keyboard — не решает задачу для GNOME/KDE |
| **KDE `fake-input` (`org.kde.kwin.fakeinput`)** | Собственный, KDE-специфичный протокол KWin: имитация нажатий/отпусканий клавиш по кодам из `linux/input-event-codes.h`, плюс отправка текста по keysym (добавлено позже) — используется, например, тачпадом KDE Connect | Работает **только под KWin**, это не кросс-десктопный стандарт — [Phabricator D23766](https://phabricator.kde.org/D23766), [fake-input.xml, plasma-wayland-protocols](https://invent.kde.org/libraries/plasma-wayland-protocols/-/blob/master/src/protocols/fake-input.xml) |
| **libei + XDG portal `InputCapture`** | Портальный механизм: приложение просит композитор «захватывать» ввод после пересечения курсором заданной невидимой границы экрана (pointer barrier), события идут через транспорт libei | Спецификация финализирована и смёржена в `xdg-desktop-portal`, реализована в `xdg-desktop-portal-gnome`; в **KDE ещё не завершено** — открытая задача [«Add support for InputCapture portal and RemoteDesktop ConnectToEIS»](https://invent.kde.org/plasma/xdg-desktop-portal-kde/-/issues/12) на `xdg-desktop-portal-kde` |

**Критически важное для архитектуры PuLinTo наблюдение**: `InputCapture`/`libei` решает **другую задачу**, а не «фоновый демон читает и опционально задерживает каждую клавишу локально». Официальная документация портала описывает назначение так: «The InputCapture portal allows capturing input events from connected physical or logical devices» именно для случаев, когда ввод физического устройства нужно **перенаправить в другое место** (удалённый рабочий стол, потоковая передача игр, программы вроде Input Leap/Synergy), триггер — пересечение курсором границы экрана («pointer barrier»), и запуск требует согласия пользователя через диалог портала при каждой сессии (кроме варианта с persistence, добавленного начиная с версии портала 1.21) — [InputCapture portal docs, xdg-desktop-portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.InputCapture.html). Это делает `InputCapture` неподходящим фундаментом для always-on фонового автопереключателя: он не предназначен держать разрешение постоянно активным без barrier-триггера и без пользовательского осознанного взаимодействия с границей экрана, и его назначение — маршрутизация ввода вовне, а не наблюдение/фильтрация локально перед доставкой фокусному приложению.

### 4.2 Что реально работает сегодня на GNOME/KDE Wayland

Прямое следствие таблицы 4.1, подтверждённое независимо несколькими источниками:

> «GNOME does not implement virtual-keyboard-unstable-v1, which blocks wtype... The only reliable path on GNOME/Wayland is ydotool via `/dev/uinput`, which bypasses Wayland restrictions at the kernel level.»

То есть даже стандартные готовые утилиты для *ввода текста программой* (`wtype`) не работают на GNOME именно потому, что `mutter` не реализует `virtual-keyboard-unstable-v1`; рабочая замена (`ydotool`) сама работает через `/dev/uinput`, то есть тем же самым механизмом, который нужен PuLinTo. Дополнительно у Wayland это не случайность, а осознанная позиция протокола: «Wayland intentionally forbids synthetic input (fake keyboard/mouse events)» — то есть для стороннего процесса нет и не планируется универсального «мягкого» способа синтезировать клавиши через сам протокол; все обходы (virtual-keyboard, fake-input, InputCapture) — точечные, по-композиторно-специфичные добавки поверх этого запрета, ни один из которых не покрывает одновременно GNOME и KDE.

**Вывод по Wayland**: `evdev`+`uinput` в 2026 году остаётся **единственным путём синтеза клавиатурного ввода, работающим одинаково под GNOME Wayland, KDE Wayland, sway, Hyprland, X11 и голой консолью TTY** — потому что он вообще не завязан на Wayland-протоколы, а работает на уровень ниже, через тот же интерфейс ядра, которым в конечном счёте питаются и libinput, и Xorg, и все композиторы разом.

## 5. Определение активного окна на Wayland (для правил «не работать в терминале»)

Единого кросс-композиторного Wayland-протокола для «какое окно сейчас в фокусе / его класс приложения» не существует по историческим и политическим причинам, что подтверждается прямым ответом мейнтейнера KWin на запрос реализовать существующий сторонний протокол:

> Запрос [«Implement wlr foreign toplevel management wayland protocol» (KDE bug #502647)](https://bugs.kde.org/show_bug.cgi?id=502647) был закрыт разработчиком KWin Владом Загороднием со статусом RESOLVED INTENTIONAL, с комментарием: «We already have a window management protocol [kde-plasma-window-management]. Perhaps you could ask activitywatch developers to add a backend that uses it.»

Это означает, что сейчас (2026) сосуществуют минимум три несовместимых механизма:

| Композитор/DE | Механизм получения активного окна | Стабильность |
|---|---|---|
| **sway** и другие wlroots-композиторы | Родной протокол `wlr-foreign-toplevel-management-unstable-v1`; практически — IPC `swaymsg -t get_tree` / подписка на события фокуса | Стандартизировано в экосистеме wlroots, документировано |
| **Hyprland** | Собственный IPC/`hyprctl`: `hyprctl activewindow -j` возвращает JSON с полем `.class` | Родной, стабильный, документированный |
| **KDE Plasma / KWin** | Собственный протокол `org.kde.plasma.window-management` + D-Bus-интерфейс `org.kde.KWin` (например, `qdbus org.kde.KWin /KWin org.kde.KWin.queryWindowInfo` возвращает `resourceClass`/`resourceName`); тот же D-Bus-путь работает и под X11, и под Wayland-сессией KWin | Родной для KDE, но несовместим с wlroots-протоколом (сознательный отказ от него, см. bug #502647) |
| **GNOME Shell (mutter)** | Нативного протокола для стороннего процесса нет вообще. Единственный путь — GNOME Shell **extension**, работающая внутри самого процесса Shell и экспонирующая D-Bus (`org.gnome.Shell.Extensions.Windows.List` у расширения `window-calls`, либо «Focused Window D-Bus» у одноимённого расширения); `WM_CLASS` всё ещё доступен внутри Shell через `Meta.Window.get_wm_class()`, но только коду, который выполняется *внутри* Shell (то есть расширению) | Зависит от стороннего расширения, которое пользователь должен сам поставить; ничего «из коробки» |

Практическое следствие для PuLinTo: правило «не работать в терминале» на Wayland **не реализуется одним универсальным способом**. Нужен per-desktop бэкенд: собственный IPC для sway/Hyprland (тривиально и стабильно), D-Bus `org.kde.KWin` для KDE (тривиально, стабильно, ничего доп. ставить не нужно), и **явная зависимость от GNOME Shell-расширения** для GNOME — то есть на «чистом» GNOME Wayland без дополнительного расширения PuLinTo не сможет узнать, какое приложение активно, и придётся либо просить пользователя поставить расширение, либо деградировать до «работать одинаково везде» (без per-app исключений) на голом GNOME.

## 6. Рекомендуемая архитектура ввода

**Основной бэкенд: `evdev` (эксклюзивный `EVIOCGRAB`) → внутренний конвейер решений → `/dev/uinput`, как единственный ввод/вывод-слой демона, одинаковый на X11, всех Wayland-композиторах и в TTY.**

Обоснование одной строкой: это единственный механизм, который (а) физически способен *задержать* событие, а не только его увидеть (в отличие от XRecord — раздел 2), и (б) работает одинаково под GNOME Wayland и KWin, которые оба **не поддерживают** `virtual-keyboard-unstable-v1` (раздел 4.1) и для которых любой Wayland-протокольный путь синтеза ввода либо не существует, либо специфичен только одному DE. X11-специфичный путь (`XGrabKey`+`XTestFakeKeyEvent`, как в xneur) не даёт ничего сверх этого, но теряет универсальность и добавляет конфликт с грабами других X-клиентов — поэтому его не стоит делать основным, разве что как fallback для сред, где `/dev/uinput` недоступен без настройки прав (см. ниже).

Из этого следует:
- **Не X11 XRecord** как основа — он структурно не может решить задачу Enter (раздел 2.1), это не вопрос реализации, а свойство протокола.
- **Не Wayland-протоколы** (`virtual-keyboard-unstable-v1`, `input-method-unstable-v2`, KDE `fake-input`, `libei`/`InputCapture`) как основа — каждый закрывает не более одного семейства композиторов, а `InputCapture`/`libei` вообще решает другую по смыслу задачу (barrier-triggered редирект ввода вовне, не локальная фильтрация, раздел 4.1).
- Практика экосистемы (`keyd`, `interception-tools`, `kmonad`, `xremap`, `evremap`) единогласно подтверждает, что `evdev`+`uinput` — стандартный путь именно для системных, DE-независимых демонов такого типа (раздел 1.2).

### Как конкретно обрабатывать Enter

Из разведки (раздел 1 и 3) следует не «изобретать логику предсказания», а **скопировать консервативный, уже проверенный десятилетиями паттерн xneur/xswitcher**, но реализовать его честно на уровне грабинга, а не эмуляции через X11:

1. **Enter (`KEY_ENTER`/`KEY_KPENTER`) не участвует в логике автоконвертации как «слово завершено, конвертируй».** Он всегда либо a) немедленно пропускается демоном не глядя (grab → сразу форвард в uinput без задержки), либо b) используется только как триггер **сброса внутреннего буфера набора** (аналог `FlushBufferWhenPressEnter`/`Drop`+`NewSentence` у xneur/xswitcher) — то есть демон забывает, что за слово было набрано, и никогда не пытается «исправить» его вдогонку.
2. Технически, поскольку демон и так эксклюзивно грабит устройство, у него физически есть возможность подержать Enter «в очереди» на несколько миллисекунд, чтобы успеть решить, нужно ли перед ним вставить Backspace+перенабор. **Разведка не нашла ни одного существующего инструмента, который бы так делал** — это осознанный отказ индустрии от игры на грани, а не забытая возможность. Рекомендация: **не делать так и в PuLinTo**. Причина: даже пара миллисекунд задержки перед Enter в терминале/чате — субъективно ощутимый лаг именно на самой частой и самой «финализирующей» клавише, а любая ошибка эвристики здесь необратима (сообщение либо уже не переписать, либо ситуация «слово исправлено, но команда в шелле уже пошла с опечаткой, а теперь после неё летит мусор из Backspace») — то есть асимметрия рисков («не исправить одно слово» против «сломать уже отправленную команду/сообщение») однозначно в пользу консервативного варианта.
3. Практическое правило для PuLinTo: **автоконвертация «на лету» триггерится только явными разделителями слова, которые сами по себе безопасны для повторной генерации** — пробел, знаки препинания, возможно Tab — и **никогда не Enter**. Дополнительно (по аналогии с Punto Switcher, раздел 3.4) стоит:
   - держать per-app список исключений (терминалы — по умолчанию в списке, независимо от результатов раздела 5 про активное окно — то есть должен работать эвристический дефолт «известные терминальные эмуляторы» даже там, где активное окно на Wayland программно не определить без стороннего расширения);
   - дать пользователю ручной хоткей «перенабрать последнее слово/фразу» (как в easy-switcher/xswitcher) как страховочный путь, полностью развязанный от автоматики и, соответственно, не имеющий гонки с Enter вообще — пользователь сам решает нажать его *до* Enter.
4. Активное-окно-детект (раздел 5) — best-effort слой поверх этого, а не основа безопасности: на sway/Hyprland/KDE он тривиален и надёжен через нативный IPC/D-Bus; на «чистом» GNOME Wayland без расширения его не будет вовсе, и в этом случае единственная защита от порчи терминалов/чатов — консервативное правило п.1–3 (Enter не триггерит конвертацию) плюс список known-terminal WM_CLASS, доступный там, где WM_CLASS/app_id вообще виден демону.
