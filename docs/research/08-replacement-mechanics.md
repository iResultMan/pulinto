# Разведка: механика замены текста в переключателях раскладки

Дата: 2026-08-01
Метод: поиск и анализ первоисточников — исходный код открытых аналогов (punto-rs, xswitcher, lay-public, easy-switcher, xneur), их README/issue-трекеры, форумные обсуждения (linux.org.ru, Habr, Yandex-блог Punto Switcher), где содержатся конкретные технические детали. Реверс-инжиниринг закрытых бинарников не проводился.

Обозначения: **[Ф]** — подтверждено первоисточником (код/README/issue проекта, официальный блог). **[В]** — вторичный источник с техническими деталями (статья, пересказ обсуждения). **[Ф-Ф]** — форумное мнение/жалоба без технического подтверждения. **[Предположение]** — наш вывод без прямого подтверждения источником.

Не по определению языка — это закрыто в файлах 01, 03. Здесь только механика замены уже набранного текста.

## 1. Что именно отправляется при замене

Три подхода подтверждаются реальным кодом/README трёх разных проектов — они не гипотетические, все три реально используются:

### (а) Backspace + перепечатать символы целевого текста

Используется там, где программа оперирует уже определённой Unicode-строкой, а не физическими нажатиями — то есть там, где у неё нет доступа к скан-кодам или где скан-коды не помогут (например, разные локальные раскладки на удалённой и локальной машине, или macOS, где нет прямого evdev-эквивалента). Не найдено ни одного open-source Linux-переключателя, который использовал бы этот метод «в чистом виде» (просто печатать целевые Unicode-символы через синтетические KeyPress с произвольными keysym) — на X11/Wayland+evdev все нашедшиеся живые проекты явно выбрали подход (б), считая его надёжнее. Печать «символами» через `XTestFakeKeyEvent` с произвольными keysym требует либо временной подмены keymap (риск конфликтов с реальной раскладкой пользователя — см. Launchpad bug #837456: `XTestFakeKeyEvent` может незапрошенно менять keyboard mapping на 'us') **[Ф]** (https://bugs.launchpad.net/bugs/837456), либо посимвольного поиска нужного keycode+уровня в текущей раскладке, что сложнее и медленнее прямого replay.

### (б) Backspace + переиграть те же физические скан-коды после переключения раскладки

Это доминирующий подход у всех живых Linux-переключателей, которые публикуют исходники:

- **punto-rs** (`netherguy4/punto-rs`, evdev/uinput) — README прямо формулирует принцип **[Ф]**:
  > «Демон хранит не символы, а скан-коды нажатых клавиш. Чтобы исправить раскладку, достаточно стереть набранное, переключить раскладку системной комбинацией и переиграть те же самые физические клавиши — система сама отдаст буквы другого алфавита.»

  Код (`src/state.rs`) буквально хранит `Stroke { code: u16, shift: bool }` — скан-код и состояние Shift, не Unicode-символ **[Ф]**.

- **xswitcher** (`ds-voix/xswitcher`) — README: «It just sends a number of BackSpaces to wipe the last input, then calls language switcher..., and then retypes the same keyboard events by means of virtual keyboard» **[Ф]** (https://github.com/ds-voix/xswitcher). Тот же принцип: переиграть исходные keyboard events, а не печатать целевые символы.

- **lay / lay-public** (`radislabus-star/lay-public`) — «физический replay через scancode», хранит «короткий хвост набора» и переигрывает после переключения раскладки **[Ф]** (https://github.com/radislabus-star/lay-public).

- **Easy Switcher** (Pascal, `freemind001/easy-switcher`) — «writes your keystrokes to internal buffer, and when you press a special key..., it erases what you have written, changes the layout, and writes the correct input back» **[Ф]** — README не детализирует, идут ли в буфер скан-коды или символы, но исторически (по описаниям на linux.org.ru) Easy Switcher работает «через чтение устройства ядра, а не xkb» **[В]**, что указывает на скан-код-ориентированный, а не символьный буфер.

Известные проблемы подхода (б), подтверждённые источниками:
1. **Зависимость от факта завершения переключения раскладки** — если реплей начинается раньше, чем система реально сменила активную раскладку, символы уходят в старой раскладке. Отсюда все три активных проекта (xswitcher, lay, punto-rs) вставляют задержку именно на этом шаге (см. §4).
2. **Модификаторы, зажатые физически пользователем** (например, Shift при вызове `Shift+Insert`), исказят реплей, если их не снять перед тем как эмулировать Shift для отдельных букв — punto-rs явно вызывает `release_modifiers()` перед началом инъекции **[Ф]** (`src/injector.rs`).
3. **Устройство должно уметь эмулировать весь диапазон кодов** — punto-rs создаёт виртуальное uinput-устройство, декларирующее коды 1..255, «чтобы не пересоздавать устройство под каждую раскладку» **[Ф]**.
4. Подход принципиально **layout-agnostic** — не обязан знать, что стоит за конкретным скан-кодом в конкретной раскладке (в отличие от подхода (а), где нужно самому знать таблицу символов раскладки) — это и есть причина, по которой все нашедшиеся проекты выбрали (б): не нужно поддерживать N раскладок вручную.

### (в) Через буфер обмена и вставку

- **RuSwitcher** (открытый клон Punto Switcher для macOS, статья на Habr) — до версии 2.2 использовал буфер обмена: `Shift+Left` для выделения → `Cmd+C` → преобразование → `Cmd+V` **[В]** (https://habr.com/ru/articles/1050394/). С версии 2.2 автор **отказался** от буфера обмена в пользу прямой печати через `CGEvent` при обычном наборе — буфер остался только там, где нет другого способа прочитать выделение (конвертация уже выделенного пользователем текста), потому что «в macOS нет API прочитать произвольное выделение иначе как через копирование» **[Ф]** (комментарии автора, https://habr.com/ru/articles/1050394/comments/).
  - Проблема буфера обмена, которую автор явно называет причиной отказа: буфер пользователя **затирается** во время операции; решение — сделать снимок содержимого буфера перед вставкой и восстановить его через ~2 секунды **[В]**.
  - Известные несовместимости: Terminal.app и iTerm2 — `Cmd+C` там генерирует SIGINT вместо копирования, то есть перехват через буфер в терминалах не работает в принципе **[В]**.
- **xneur, issue #42** — показывает обратный сценарий: **непреднамеренное** протекание буфера обмена в замену как баг, а не фичу. При быстром нажатии Pause/Break сразу после набора слова xneur иногда вместо коррекции набранного стирает текст и **вставляет содержимое системного буфера обмена** (в неправильной раскладке) **[Ф]** (https://github.com/AndrewCrewKuznetsov/xneur-devel/issues/42). Особо неприятный случай: если в буфере многострочный текст, туда попадают Enter-ы, которые в мессенджерах (Pidgin) отправляют сообщение раньше времени. Это косвенно говорит, что где-то во внутренней логике xneur замена **временно перекладывает буфер обмена**, а не работает только с локальным буфером скан-кодов — то есть xneur, в отличие от punto-rs/xswitcher/lay, где-то в тракте использует системный clipboard, и это источник данного бага **[Предположение из косвенных данных issue]**.

**Вывод по вопросу 1**: На Linux у всех активно поддерживаемых open-source проектов, дошедших до рабочего состояния, победил подход (б) — скан-код-реплей. Подход (а) в чистом виде не встретился ни в одном рабочем Linux-проекте. Подход (в) — либо вынужденная мера там, где нет низкоуровневого доступа к вводу (macOS-клон RuSwitcher до v2.2), либо источник багов, когда просачивается туда, где не должен (xneur issue #42).

## 2. Порядок операций и синхронизация со сменой раскладки

Явный, задокументированный в коде порядок — **punto-rs**, `src/injector.rs`, метод `fix()` **[Ф]**:

```
1. release_modifiers()           — снять физически зажатые модификаторы
2. sleep(key_delay_ms)
3. N × tap(BACKSPACE, key_delay_ms)   — стереть все скан-коды буфера
4. sleep(post_backspace_ms)       — дать приложению доесть Backspace-ы
5. combo(layout_switch, key_delay_ms)  — переключить раскладку
6. sleep(switch_delay_ms)         — ЖДАТЬ, пока раскладка реально переключится
7. retype strokes (с Shift там, где нужно)
```

То есть порядок однозначный: **сначала полностью стереть, потом переключить раскладку, и только потом печатать** — печать никогда не идёт параллельно с переключением. Гонка «раскладка ещё не переключилась, а символы уже пошли» устраняется не подтверждением от системы (никакого ожидания события смены раскладки в коде нет), а **фиксированной задержкой** `switch_delay_ms` после отправки комбинации переключения — то есть это не синхронизация по событию, а расчёт по времени (race avoided by timing margin, not by acknowledgement) **[Ф, вывод из кода]**.

Это подтверждается и независимым проектом: **lay-public** прямо говорит, что перед replay «снова обязательно синхронизируются GNOME Shell и IBus, чтобы браузеры успевали принять фактическую раскладку» **[Ф]**, и что дебаг-лог показывает разбивку по стадиям `layout → delete → insert/replay → total` — то есть переключение раскладки в их коде тоже отдельная измеримая стадия, которую ждут завершить перед печатью, а не оптимистично гонят её параллельно с текстом.

**xswitcher** аналогично: порядок «Backspace → language switcher → retype», с отдельным `Delay` под Wayland именно на переключение раскладки, потому что «занимает около 50мс на моей KDE» **[Ф]**.

Никто из нашедшихся проектов **не ждёт явного подтверждения от системы** (событие типа `XkbStateNotify` или D-Bus сигнал о смене layout) перед тем как начать печатать — везде это эмпирически подобранная константа задержки. Единственное исключение с элементом синхронизации по событию — **lay** упоминает синхронизацию с GNOME Shell/IBus «через DBus-bridge» перед replay, что ближе к ожиданию подтверждения, чем просто taймер, но детали (ждут ли именно ack, или тоже используют паузу после DBus-вызова) источник не раскрывает подробно **[В, требует уточнения]**.

## 3. Что делать с разделителем (пробелом)

Два задокументированных подхода, оба — «стереть вместе со словом и набрать заново», ни один найденный живой проект **не** уводит курсор влево-вправо для правки на месте:

- **punto-rs**: явно включает **хвостовые разделители** в стираемый и перепечатываемый диапазон. Комментарий в коде `src/state.rs`, метод `last_word()` **[Ф]**:
  > «Хвост включается намеренно: курсор стоит уже после пробела, поэтому стирать и набирать заново надо вместе с ним, иначе слово склеится.»

  Разделитель (Tab/Space) при этом воспроизводится «как есть» — его скан-код одинаков в обеих раскладках (`src/keys.rs`, комментарий: «Разделители слов: их скан-коды одинаковы в любой раскладке, поэтому при переигрывании они воспроизводятся как есть» **[Ф]**).

- **lay**: работает в «smart»-режиме, который «не трогает уже нормальные соседние слова» — пример из источника: `good ntrcn -> good текст`, соседнее слово `good` не переписывается **[Ф]**. То есть граница слова определяется, но конкретно вопрос курсора-после-пробела решается так же — переписывается только последнее слово (с его собственным хвостом), а не всё поле.

Подход «увести курсор влево, поправить, вернуть вправо» **не встретился ни в одном источнике** как реально реализованный — вероятно потому что курсорные операции (стрелки, `Home`) сами по себе имеют собственную, менее предсказуемую семантику в разных приложениях (автодополнение может реагировать на движение курсора иначе, чем на ввод символов), тогда как Backspace+ретайп остаётся семантически «просто ещё одним вводом текста» с точки зрения приложения. Это объяснение — **[Предположение]**, прямо источники так не аргументируют, но косвенно оно согласуется с тем, что punto-rs явно сбрасывает буфер «на любой навигации (стрелки, Home, Delete)» именно потому что «накопленное перестаёт соответствовать тексту на экране» (`src/main.rs`, комментарий) **[Ф]** — то есть сам проект трактует курсорную навигацию как разрушающую инвариант буфера, а не как безопасный инструмент правки.

Известные проблемы по типам приложений (из форумных источников, все — жалобы на автозамену в целом, не именно на разделитель, но релевантны):
- **Терминал**: Punto Switcher «не подходит программистам и администраторам» — может переключить раскладку не вовремя, например при вводе пароля **[Ф-Ф]** (ru-board.club, обобщённая жалоба).
- **RDP/удалённый рабочий стол**: если Punto Switcher установлен и на локальной, и на удалённой машине, коррекция срабатывает **дважды** — «Один раз благодаря Punto на удалённой машине, второй раз благодаря Punto на локальной машине», в результате текст остаётся некорректным. Разработчик прямо признаёт: «не можем гарантировать правильную работу программы в случаях, когда используются удалённый доступ, виртуальные среды» **[Ф]** (https://yandex.ru/blog/punto/10499).
- **Игры**: производительность может страдать; Caramba Switcher, по описанию, «самостоятельно отключается в играх» **[В]** — то есть эталонная реализация просто не пытается решить проблему разделителя/замены в играх, а исключает класс приложений целиком.

## 4. Тайминги

Единственные три источника с конкретными числами:

| Проект | Параметр | Значение | Контекст |
|---|---|---|---|
| xneur | `SendDelay` | по умолчанию `0` — «задержка перед отправкой перехваченного нажатия клавиши обратно приложению» **[Ф]** (https://habr.com/ru/articles/132635/) | Конкретных рекомендованных ненулевых значений и количественных жалоб «слишком быстро/медленно» в найденных источниках нет — есть только жалобы общего характера на нестабильность xneur («глюки», «бред при вводе»), без привязки к конкретному значению SendDelay **[Ф-Ф]** |
| xswitcher | `Delay` (Wayland) | по умолчанию `50` мс | Обоснование в README: «It takes about 50 ms to complete switching the keyboard layout in my KDE, so I set 50 as the default value» **[Ф]** — то есть это эмпирическая оценка одного автора под одну DE, не универсальная константа |
| lay | измеренные стадии | короткое слово ≈ 53–62 мс (основной остаток — переключение layout); 2–3 слова ≈ 40 мс; typing-assist после пробела ≈ 61–75 мс; длинный хвост (~240 симв.) ≈ 1.1 с с «pacing для безопасности» **[Ф]** | Явно требует «pacing» — то есть по мере роста числа переигрываемых нажатий задержки не убираются, чтобы не терять символы |
| punto-rs (собственный код) | `key_delay_ms`, `post_backspace_ms`, `switch_delay_ms` | конкретные значения не зашиты — вынесены в конфиг, разделены на три независимых параметра под три разных стадии (между нажатиями / после добивания backspace / после переключения раскладки) **[Ф, из кода]** | Разделение на три отдельных таймаута — единственный найденный пример, где задержка после переключения раскладки явно отделена от задержки между отдельными нажатиями |

Прямых форумных жалоб «слишком быстро — глотает буквы» / «слишком медленно — раздражает» с конкретными числами найти не удалось; форумные ветки про SendDelay в основном свелись к общим оценкам xneur как «глючного» инструмента без привязки к конкретной задержке **[Ф-Ф]** (https://www.linux.org.ru/forum/general/14601665, https://www.linux.org.ru/forum/desktop/15526726). Отдельно зафиксирован баг «Google Chrome печатает несколько букв при одном нажатии» после xneur **[Ф-Ф, форумный пересказ]** — по характеру напоминает эффект от таймингов/keyrepeat, но источник не даёт причинного анализа.

## 5. Эхо и петли

Единственный источник с явным, кодово подтверждённым решением — **punto-rs**:

1. **Собственное виртуальное устройство исключается по имени** из списка прослушиваемых устройств: `attach_devices()` явно пропускает устройство, чьё имя совпадает с именем виртуальной клавиатуры демона (`if name == VIRTUAL_NAME { continue; }`) **[Ф]**. То есть демон в принципе не может услышать собственный инжект как «эхо» — не нужно фильтровать по признаку синтетичности события, петля обрывается на уровне выбора источника.
2. **Явный дренаж очереди после инъекции**: сразу после `injector.fix(...)`, код делает `while rx.try_recv().is_ok() {}` — «Отбрасываем всё, что накопилось за время инжекта» **[Ф]**. Это отдельная защита не от эха самого инжекта (оно и так не может прийти — см. п.1), а от того, что реальные физические клавиши пользователя, нажатые **во время** работы инъекции (стирание+переключение+перепечатка занимает десятки-сотни мс), не будут неправильно истолкованы как продолжение старого буфера после того, как буфер уже был переигран.
3. Осознанный компромисс по поводу «не грабить устройство» (`EVIOCGRAB` не вызывается): README прямо объясняет причину и цену **[Ф]**:
   > «Ключевое отличие от Easy Switcher: клавиатура не перехватывается (EVIOCGRAB не вызывается). Easy Switcher забирал устройство себе и переизлучал каждое нажатие — на этом он терял буквы при быстром наборе. Здесь чтение пассивное... Плата за это — горячая клавиша долетает и до активного приложения, поэтому её стоит выбирать безвредной: Pause/Break не делает ничего нигде.»

   Это прямое свидетельство компромисса «эксклюзивный граб устройства» vs «пассивное чтение + аккуратный выбор хоткея» — Easy Switcher выбрал первое и заплатил потерей букв при быстром наборе **[Ф, из README punto-rs, пересказывающего проблему Easy Switcher]**; более подробного технического разбора именно механизма потери букв в самом Easy Switcher (буферизация, блокировка на переизлучении) в его собственном README не найдено.

## 6. Отмена замены

- **Punto Switcher (Windows)**: механизм отмены — повторное нажатие той же горячей клавиши (по умолчанию Pause/Break, либо переназначенная пользователем комбинация), которое «откатывает» только что сделанную замену обратно **[Ф-Ф]** (множественные форумные источники и официальный блог единогласны в этом описании, например https://yandex.ru/blog/punto/12814). Технических деталей — сколько именно Backspace-ов посылается при откате, восстанавливается ли исходная раскладка, что происходит с внутренним буфером слова после отката, что если пользователь успел напечатать что-то ещё после замены — **в открытых источниках не найдено**; официальная документация описывает только пользовательское поведение («нажмите Pause ещё раз»), не внутренний механизм. Есть отдельные жалобы «отмена невозможна» в некоторых сценариях, но без анализа причины **[Ф-Ф]**.
- **Caramba Switcher**: отдельной «кнопки отмены» не описано; вместо неё — превентивный механизм обучения на исключениях: если слово переключилось неправильно, пользователь стирает его Backspace-ом и печатает снова (обычный набор, без специальной комбинации отмены), после чего Caramba сама предлагает создать исключение — то есть у Caramba «отмена» = обычное ручное стирание + повторный набор + фиксация как правила на будущее, а не программный откат состояния **[В]**.
- **punto-rs (эталонная своя реализация)**: специального механизма отмены **не реализовано** — буфер скан-кодов пересобирается заново из физических событий после срабатывания хоткея (пункт 5, дренаж очереди), но обратного отката именно последней замены в коде не найдено; это архитектурный пробел, который стоит явно закрыть в PuLinTo (см. рекомендации ниже) **[Ф, вывод из отсутствия соответствующего кода]**.
- **lay**: документация упоминает, что для отката можно использовать «user feedback», но специального встроенного undo не описано — полагается на стандартный `Ctrl+Z` самого приложения **[В]**.

Вывод: ни один из активно поддерживаемых Linux-переключателей с открытым кодом не реализует полноценный программный undo замены (восстановление скан-кодов + обратное переключение раскладки). Единственный пример полноценного UX-уровня «отмена по хоткею» — закрытый Punto Switcher, чья внутренняя механика не опубликована.

## Рекомендуемая механика замены для PuLinTo

Опираясь на разобранный код punto-rs (это уже эталонная для нас реализация подхода "б", которая по всем найденным источникам совпадает с тем, что делают живые открытые Linux-переключатели) и на выявленные слабые места (нет undo, есть открытая проблема с двойной коррекцией под RDP, потенциальные проблемы с терминалами/играми), пошаговый алгоритм:

### Что хранить в буфере
- Скан-код (`code: u16`) + состояние Shift на момент нажатия — **не** Unicode-символ. Причина: это единственный способ оставаться layout-agnostic и не поддерживать вручную таблицы символов под каждую пару раскладок (см. §1).
- Хвостовые разделители (Space/Tab) включаются в диапазон стирания/перепечатки вместе со словом — иначе слово, склеенное с последующим текстом, разъедется (см. §3).
- Дополнительно к тому, что уже есть в punto-rs, — хранить **снимок для отмены**: перед тем как разрушить текущий буфер новой инъекцией, сохранять последний применённый `Vec<Stroke>` вместе с раскладкой, которая была активна **до** замены (для undo, см. ниже). Это закрывает пробел §6 — единственный найденный undo-механизм у аналогов держится либо в закрытом Punto Switcher, либо не описан вовсе.

### Порядок отправки (эмуляция физических нажатий, не печать символов)
1. Снять физически удерживаемые модификаторы (Shift/Ctrl/Alt/Meta) — иначе они исказят реплей.
2. Подождать `key_delay_ms`.
3. Отправить N нажатий Backspace (по числу скан-кодов в стираемом диапазоне), с паузой `key_delay_ms` между down/up каждого.
4. Подождать `post_backspace_ms` — дать приложению обработать все Backspace-ы, прежде чем трогать раскладку.
5. Отправить комбинацию переключения раскладки.
6. Подождать `switch_delay_ms` — **не** пытаться дождаться подтверждающего события от системы (никто из разобранных проектов так не делает; см. §2); вместо этого держать это значение настраиваемым и достаточно большим с запасом, отдельно от `key_delay_ms`.
7. Переиграть сохранённые скан-коды (с Shift там, где нужно), каждый — down/`key_delay_ms`/up/`key_delay_ms`.

Три отдельных таймаута (`key_delay_ms`, `post_backspace_ms`, `switch_delay_ms`) — не один общий `SendDelay`, как в xneur. У xneur это единственный параметр под все случаи и ноль по умолчанию — судя по репутации проекта («глючный», «бред при вводе», гонки с KDE Plasma), это, вероятно, часть проблемы. lay и xswitcher независимо друг от друга выделяют именно стадию переключения раскладки как отдельно измеряемую и самую долгую (40–75 мс на слово, до 50 мс только на сам layout switch) — так что `switch_delay_ms` стоит по умолчанию держать заметно больше, чем `key_delay_ms`.

### Задержки (стартовые значения, требуют калибровки на целевых DE)
- `key_delay_ms` — единицы миллисечунд (punto-rs — параметр, не значение по умолчанию; xswitcher использует 50 мс совокупно на весь layout switch, не на отдельное нажатие).
- `post_backspace_ms` — небольшой, для гарантии что приложение доело Backspace-ы перед сменой раскладки.
- `switch_delay_ms` — стартово 50 мс (эмпирика xswitcher под KDE), с пометкой, что реальное время зависит от DE/композитора и должно быть настраиваемым, а не жёстко зашитым.
- Общий принцип из lay: при увеличении объёма переигрываемого текста (`Shift+Insert` на всю фразу) — задержки не убирать, а масштабировать («pacing для безопасности»), иначе на длинных фразах теряются символы.

### Эхо/петли
- Не грабить устройство ввода (`EVIOCGRAB` не вызывать) — пассивное чтение, как в punto-rs, дороже потерей отклика на «безвредность» хоткея, но безопаснее, чем граб + переизлучение (Easy Switcher терял буквы при быстром наборе именно из-за граба).
- Собственное виртуальное uinput-устройство исключать из списка прослушиваемых по имени — тогда защита от эха не нужна вообще, петля отсутствует структурно.
- После завершения инъекции — дренировать очередь событий, накопившихся за время работы инъекции, чтобы физические нажатия пользователя во время замены не были неправильно приписаны старому буферу.

### Отмена замены (то, чего не хватает punto-rs и большинству аналогов)
1. Хранить последний применённый `Vec<Stroke>` + раскладку до замены как отдельное состояние `last_fix`, независимое от текущего рабочего буфера.
2. По отдельному хоткею отмены: стереть ровно столько символов, сколько было напечатано при последней замене (включая хвостовой разделитель, если он был перепечатан), переключить раскладку обратно на сохранённую «раскладку до замены», переиграть исходные скан-коды из `last_fix`.
3. `last_fix` должен инвалидироваться при любом дальнейшем вводе пользователя после замены (аналогично тому, как punto-rs сбрасывает рабочий буфер на курсорной навигации/Ctrl-комбинациях) — иначе отмена «через несколько слов» откатит не то, что пользователь ожидает.
4. Явно не пытаться реализовать undo через восстановление буфера обмена — это единственный из трёх подходов (§1в), который у существующих аналогов оказывается источником багов (xneur issue #42), а не решением.

### Подводные камни, которые стоит закладывать в архитектуру заранее
- **RDP/VNC**: если PuLinTo может оказаться установлен и на клиенте, и на сервере одновременно — предусмотреть детектирование такого окружения и явное отключение (Punto Switcher этот случай прямо признаёт неподдерживаемым).
- **Игры**: exclusion list по умолчанию — не чинить механику под fullscreen/DirectX-подобные поверхности, а не пытаться туда попасть вообще (Caramba Switcher поступает так же).
- **Терминалы/пароли**: exclusion list или отдельный "осторожный" режим для терминальных эмуляторов — жалобы на срабатывание не вовремя (в т.ч. при вводе пароля) системные для всей категории приложений, не специфичны для одного переключателя.
- **DE-зависимые гонки** (KDE Plasma + смена окна): не полагаться на то, что DE сама сообщит о фокусе/раскладке вовремя — там, где возможно, брать управление отслеживанием фокуса окна на себя, а не доверять композитору (это буквально сработавший обходной путь из ветки про xneur+Plasma 5).
- **Электрон/Chrome-подобные (сильное предположение, не подтверждено первоисточником)**: жалобы на дублирование букв при инъекции в Chrome требуют собственной проверки на целевых версиях — в найденных источниках нет технического разбора причины, только симптом.
