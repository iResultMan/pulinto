## 1. Есть ли у Mahou автоматический режим (без хоткея)?

**Нет.** Это [код] и [веб] подтверждается независимо в трёх местах:

- Точка входа в перехват — глобальный `WH_KEYBOARD_LL`-хук, но конверсия текста запускается только когда нажатая комбинация совпадает с одним из настроенных хоткеев (`HKCLast`, `HKCSelection`, `HKCLine`) — `Mahou/Classes/KMHook.cs:121-230` (блок `#region Hotkeys`), конкретно строки 143, 165, 187: `if(thishk.Equals(MMain.mahou.HKCSelection) && hksOK) {…}` и аналогично для `HKCLast`/`HKCLine`.
- Я искал по всему дереву репозитория признаки словарного/статистического автоопределения раскладки (`grep -rniE "dictionary|word.?list|spell|automatic"`) — ничего, кроме UI-текста `AutoScaleMode`/`Autostart`/`Auto Update`, не связанного с определением раскладки, не нашёл.
- README.md (英/рус, [веб]) прямо описывает три способа конверсии, и все три — по хоткею: `README.md:11-16` (рус.) / `README.md:111-116` (англ.): *"1. Для конвертации выделения нажмите `Scroll`… 2. Для конвертации последнего введенного слова нажмите `Pause`… 3. …`Shift`+`Pause`"*.

Единственное, что похоже на «фон» — таймер `ICheck` в `Mahou/MahouForm.cs:45-64`, который каждые `DLRefreshRate` мс сравнивает текущую раскладку (`Locales.GetCurrentLocale()`) с предыдущей и **показывает всплывающую подсказку** (`langDisplay.ShowInactiveTopmost()`), не трогая текст:

## 2. Как выполняется замена

Здесь у Mahou **два принципиально разных механизма**, в зависимости от того, какую функцию дёргает хоткей, и это прямо отвечает на подозрение задания ("на Windows текст вставляют напрямую Unicode-ом").

### 2a. `Convert word` / `Convert line` (Pause / Shift+Pause) — НЕ Unicode-инъекция

Метод `ConvertLast` — `Mahou/Classes/KMHook.cs:736-775`. Алгоритм:
1. `self = true; var wasLocale = Locales.GetCurrentLocale(); ChangeLayout();` (строки 741-743) — **сначала переключает системную раскладку**.
2. Стирает N символов бэкспейсом: `KInputs.MakeInput(new[] { KInputs.AddKey(Keys.Back, true), KInputs.AddKey(Keys.Back, false) });` (строки 746-749).
3. Заново "нажимает" **те же самые** virtual-key коды, что были записаны при исходном наборе (`YuKeys[i].yukey`), через `KInputs.AddKey`, а НЕ через Unicode:
```
Mahou/Classes/KMHook.cs:762-770
if(YuKeys[i].upper)
    KInputs.MakeInput(new[] { KInputs.AddKey(Keys.LShiftKey, true) });
if(!SymbolIgnoreRules(YuKeys[i].yukey, YuKeys[i].upper, wasLocale)) {
    KInputs.MakeInput(new[] { KInputs.AddKey(YuKeys[i].yukey, true) });
    KInputs.MakeInput(new[] { KInputs.AddKey(YuKeys[i].yukey, false) });
}
```
`KInputs.AddKey` (`Mahou/Classes/KInputs.cs:58-77`) собирает `INPUT` с `Vk = vk` и `Scan = MapVirtualKey(vk, 0)`, **без** `KEYEVENTF_UNICODE`. То есть это классическая схема "бэкспейс + переигровка тех же клавиш" — тот же приём, что и у PuLinto, только на скан-кодах Windows. Правильность результата целиком зависит от того, что раскладка **уже переключилась** до начала переигровки — то есть Mahou здесь подвержен ровно той же гонке, которую мы ловим на Linux.

### 2b. `Convert selection` (Scroll) — зависит от опции `CSSwitch`

Метод `ConvertSelection` — `Mahou/Classes/KMHook.cs:549-704`. Текст сначала копируется через эмуляцию Ctrl+Insert и `NativeClipboard.GetText()` (`MakeCopy()`, строки 705-715).

- **Если `CSSwitch == true` (значение по умолчанию, `Configs.cs:86-87: this.Write("Functions", "CSSwitch", "true")`)**: код тоже вызывает `ChangeLayout()` (строка 591) и посимвольно "перепечатывает" через `KInputs.AddKey` с вычисленным `VkKeyScanEx`, то есть опять скан-код-схема, зависящая от переключённой раскладки.
- **Если `CSSwitch == false`** (пользователь явно выключил): раскладка **не трогается вообще**. Вместо этого для каждого символа исходного текста вызывается `InAnother(c, l2, l1)` / `InAnother(c, l1, l2)` (строка 668-677), которая через `VkKeyScanEx`+`ToUnicodeEx` **вычисляет**, каким символом является `c`, если бы он был набран в другой раскладке — чисто табличное преобразование символ→символ без переключения активной раскладки:
```
Mahou/Classes/KMHook.cs:891-906
static string InAnother(char c, uint uID1, uint uID2) {
    var chsc = VkKeyScanEx(c, (IntPtr)uID1);
    …
    var ant = ToUnicodeEx((uint)chsc, (uint)chsc, byt, s, s.Capacity, 0, (IntPtr)uID2);
    return chsc != -1 ? s.ToString() : "";
}
```
Готовая строка `result` вставляется одним вызовом:
```
Mahou/Classes/KMHook.cs:683
KInputs.MakeInput(KInputs.AddString(result));
```
`KInputs.AddString` (`Mahou/Classes/KInputs.cs:100-145`) — вот здесь действительно `KEYEVENTF_UNICODE`:
```
Mahou/Classes/KInputs.cs:106-119
var down = new INPUT { … Data = { Keyboard = new KEYBDINPUT {
    Vk = 0,
    Flags = KEYEVENTF_UNICODE,
    Scan = (UInt16)s,   // сам символ, не скан-код клавиши
    …
```
и отправляется через `SendInput`:
```
Mahou/Classes/KInputs.cs:146-149, 152-153
public static void MakeInput(INPUT[] inputs) {
    SendInput((UInt32)inputs.Length, inputs, Marshal.SizeOf(typeof(INPUT)));
}
…
static extern UInt32 SendInput(UInt32 numberOfInputs, INPUT[] inputs, Int32 sizeOfInputStructure);
```

**Итог по п.2:** прямая Unicode-инъекция (`SendInput`+`KEYEVENTF_UNICODE`) в Mahou есть, но она используется только в одном из четырёх путей конверсии (Convert Selection с выключенным CSSwitch), и она не единственный/не основной механизм — Mahou по умолчанию для всех трёх горячих клавиш всё равно зависит от переключения системной раскладки и переигровки скан-кодов, то есть подвержен тем же гонкам, что и мы. Кроме того, `KInputs.AddString` вызывается и в других местах не как основной путь конверсии, а для служебных вставок — например, сниппетов (`KMHook.cs:279,284`) и "переписывания" нераспознанных символов при `CSSwitch=true` (`KMHook.cs:646-651`, символы вроде "♥", которых нет ни в одной раскладке).

## 3. Переключает ли Mahou системную раскладку — и когда

Да, переключает, и в большинстве путей — **до** вставки:

- `ConvertLast`/`ConvertLine`: `ChangeLayout()` вызывается первой строкой внутри `self=true` блока, **до** цикла бэкспейсов и до переигровки клавиш (`KMHook.cs:742-745`).
- `ConvertSelection` при `CSSwitch=true`: `ChangeLayout()` вызывается после `MakeCopy()`, до посимвольной переигровки (`KMHook.cs:591`).
- `ConvertSelection` при `CSSwitch=false`: раскладка **не переключается** вовсе (см. п.2b) — единственный путь, где после замены раскладка остаётся той же, что была.

Куда указывает раскладка **после** замены: `ChangeLayout()` (`KMHook.cs:839-857`) всегда переключает на "другую" из двух настроенных (`notnowLocale`), то есть **на целевую** раскладку — логика та же, что и у нас: если слово набрано не в той раскладке, после исправления пользователь должен продолжать печатать уже в правильной.

Отдельно: `ChangeLayout` сам по себе не единственный способ переключения раскладки в проекте — есть ещё режим "Switch only key" (CapsLock/LCtrl/RCtrl как чистое переключение раскладки, без конверсии текста) — `KMHook.cs:320-373`, и "Cycle Mode" (`CycleSwitch()`, `KMHook.cs:858-890`), который либо тоже шлёт `WM_INPUTLANGCHANGEREQUEST`, либо (если включена опция `EmulateLayoutSwitch`) эмулирует физическую комбинацию Alt+Shift / Ctrl+Shift / Win+Space через `KInputs.MakeInput`. Наличие этой опции — прямое признание автора, что программное сообщение `WM_INPUTLANGCHANGEREQUEST` не всегда срабатывает, и нужен запасной путь через "настоящую" горячую клавишу — см. подсказку в UI (п.4 ниже).

## 4. Как дожидается применения смены раскладки

`ChangeLayout()` — `Mahou/Classes/KMHook.cs:839-857`:
```
static void ChangeLayout() {
    var nowLocale = Locales.GetCurrentLocale();
    uint notnowLocale = …;
    if(!MMain.MyConfs.ReadBool("Functions", "CycleMode")) {
        int tries = 0;
        while(Locales.GetCurrentLocale() == nowLocale) {
            PostMessage(Locales.ActiveWindow(), KInputs.WM_INPUTLANGCHANGEREQUEST, 0, notnowLocale);
            Thread.Sleep(50);//Give some time to switch layout
            tries++;
            if(tries == 3)
                break;
        }
    } else
        CycleSwitch();
}
```
Это **опрос с подтверждением, не фиксированная задержка**: шлёт `PostMessage(…, WM_INPUTLANGCHANGEREQUEST, …)` активному окну, спит 50 мс, затем **перечитывает фактическую раскладку через `GetKeyboardLayout`** (`Locales.GetCurrentLocale()`, `Locales.cs:11-16`) и повторяет, если не изменилось — максимум 3 попытки (то есть до 150 мс), после чего сдаётся молча (без ошибки — код просто выходит из цикла и продолжает, даже если раскладка не поменялась). Собственно подтверждение — это активный опрос состояния через `GetKeyboardLayout`, а не событие/колбэк.

Отдельно есть более "силовой" путь через опцию `EmulateLayoutSwitch`/`Emu` (подсказка в UI прямым текстом объясняет, зачем она нужна) — `Mahou/Classes/Translation.cs:34` (`ToolTipsEN[0]`):
> *"While this option enabled, [Convert word] and [Convert line] and [Convert selection with "CS-Switch" enabled] will just cycle between all locales instead of switching between selected in settings. **This mode works for almost all programs.** If there is program in which [Convert word] or [Convert line] or [Convert selection with "CS-Switch" enabled] **not work**, try with this option enabled."*

Это прямое признание: программное сообщение `WM_INPUTLANGCHANGEREQUEST` не работает во всех приложениях, и обходной путь — эмулировать физическую комбинацию клавиш пользователя (Alt+Shift / Ctrl+Shift / Win+Space) через `KInputs.MakeInput`, а не системное сообщение (`CycleSwitch()`, `KMHook.cs:858-890`). То есть даже на Windows переключение раскладки API-вызовом ненадёжно в части приложений — Mahou обходит это тем же классом трюков (эмуляция реальных клавиш), что доступен и нам через uinput/XTEST.

## Windows: вставка текста без смены раскладки

### Что делает `SendInput` + `KEYEVENTF_UNICODE`

[веб] По документации Microsoft (`learn.microsoft.com/.../ns-winuser-keybdinput`, структура `KEYBDINPUT`):

- Если `dwFlags` содержит `KEYEVENTF_UNICODE`, то `wVk` **обязан быть 0** (виртуальная клавиша не участвует), а `wScan` — это **сам символ Unicode** (UTF-16 code unit), который нужно отправить.
- Механизм: `SendInput` кладёт в очередь сообщений **активного окна** `WM_KEYDOWN`/`WM_KEYUP` с `wParam = VK_PACKET`. Когда приложение прогоняет это сообщение через `TranslateMessage` (стандартный шаг цикла сообщений Win32), система сама генерирует `WM_CHAR` **с уже готовым Unicode-символом**, взятым из `wScan`. Дословно: *"passing the message to TranslateMessage posts a WM_CHAR message with the Unicode character originally specified by wScan"*.
- Это прямо описано в документации как канал для **неклавиатурного** ввода — распознавания речи/рукописного текста: *"INPUT_KEYBOARD supports nonkeyboard-input methods—such as handwriting recognition or voice recognition—as if it were text input by using the KEYEVENTF_UNICODE flag"*.

Ключевой для нас факт: **символ уже вычислен на стороне отправителя** (это просто code unit, не скан-код и не virtual-key) — таблица раскладка→символ вообще не участвует в доставке этого конкретного события. Активная раскладка при этом никак не проверяется и не меняется этим вызовом — Mahou это и использует в пути 2b (п.2), заранее вычисляя нужный символ через `VkKeyScanEx`/`ToUnicodeEx` (по столбцу нужной раскладки), а не полагаясь на текущую активную раскладку ОС.

### Ограничения

1. **Игры / RawInput / DirectInput.** `SendInput` кладёт событие в очередь сообщений окна; приложения, читающие ввод через RawInput/DirectInput (в обход очереди сообщений), это событие не увидят. [веб, WebSearch]: подтверждается практикой автоматизаторов (AutoHotkey community, `autohotkey.com/boards/viewtopic.php?...t=38118`): "SendInput doesn't work in a game" — типичная причина в том, что игра читает устройство напрямую, а не через оконную очередь.
2. **Консольные приложения (cmd.exe/conhost).** Задокументированная проблема: [веб] `github.com/microsoft/terminal/issues/12977` — *"Sending unicode character via KEYEVENTF_UNICODE/VK_PACKET in SendInput outputs the wrong characters"* — `VK_PACKET`, порождённый `KEYEVENTF_UNICODE`, не всегда корректно долетает как символ до консольных приложений, читающих `ReadConsoleInput`, в отличие от GUI-приложений, стоящих на стандартном цикле `GetMessage`/`TranslateMessage`.
3. **Античит и детект инжекции.** [веб] По документации Microsoft (`learn.microsoft.com/.../ns-winuser-kbdllhookstruct`, структура `KBDLLHOOKSTRUCT`, используемая в `WH_KEYBOARD_LL`-хуках): бит 4 флагов (`LLKHF_INJECTED`, `0x00000010`) явно помечает событие как **инжектированное программно** (в отличие от «настоящего» железного нажатия), а бит 1 (`LLKHF_LOWER_IL_INJECTED`) — что инжекция пришла из процесса с более низким уровнем целостности. Это системная, официально задокументированная метка, по которой любое приложение (включая античит) может отличить `SendInput`-события от реальных. WebSearch по теме подтверждает, что это используется как раз для детекта/блокировки синтетического ввода в играх с античитом.

Вывод по ограничениям: `KEYEVENTF_UNICODE` — не универсальный «бесплатный» способ вставки текста в обход раскладки; он надёжен для обычных GUI-приложений на стандартном цикле сообщений (то есть для подавляющего большинства текстовых редакторов, браузеров, офисных программ — собственно, основной сценарий текстового переключателя раскладки), но не для консолей, игр и низкоуровневого чтения ввода.

### Почему Punto Switcher (predполагаемо) надёжнее линуксовых аналогов

Здесь важна честность: у меня нет исходников Punto Switcher (закрытый код Яндекса) — это рассуждение по структурным свойствам платформы, подкреплённым найденным выше в документации и в коде Mahou, а не прямая цитата из Punto. Помечаю явно как вывод/гипотезу, не как факт с строкой кода:

- Структурно у Windows есть **отдельный канал доставки текста**, не завязанный на активную раскладку: `VK_PACKET`→`WM_CHAR` с готовым Unicode code unit. Он существует именно потому, что Windows изначально проектировала ввод текста как отделённый от "нажатия физической клавиши по столбцу раскладки" — этот канал официально предназначен для IME/handwriting/speech (см. цитату выше), то есть Punto Switcher технически может (не обязан, но может) писать целевой символ напрямую, вообще не трогая `GetKeyboardLayout`/`ActivateKeyboardLayout`, если авторы выбрали этот путь — ровно как это делает необязательный путь Mahou (п.2b) при `CSSwitch=false`.
- Даже когда переключатель на Windows **всё же** меняет раскладку (как Mahou по умолчанию — см. п.2, 3), у Windows есть однозначный синхронный способ **проверить**, что переключение случилось: `GetKeyboardLayout(threadId)` — прямой опрос, без необходимости слушать шину и гадать, пересобрал ли IME своё состояние (что в нашем случае с IBus происходит асинхронно, через D-Bus). Mahou именно так и подтверждает переключение (п.4) — циклом `while(GetCurrentLocale()==old) { PostMessage(...); Sleep(50); }`.
- Важная оговорка, ослабляющая тезис задания "на Windows проблемы нет по построению": сам Mahou **не избегает гонки полностью** — он **тоже** подвержен состоянию "PostMessage отправлен, а раскладка ещё не переключилась", и **тоже** вынужден городить опрос с таймаутом (150 мс, 3 попытки) плюс запасной путь через эмуляцию реальной горячей клавиши (`EmulateLayoutSwitch`), потому что `WM_INPUTLANGCHANGEREQUEST` не гарантированно применяется синхронно и не во всех приложениях (см. цитату из tooltip в п.4). То есть проблема "переключение раскладки — асинхронное и не всегда наблюдаемое событие" существует и на Windows; разница не в том, что там гонки нет, а в том, что (а) там есть путь текстовой инъекции, который вообще не требует переключения раскладки (VK_PACKET/WM_CHAR), и (б) даже когда раскладка переключается, у неё есть простой синхронный API опроса состояния (`GetKeyboardLayout`) без посредника вроде шины IBus.

## Что из этого переносимо на Linux/X11

### Есть ли в X11 аналог "вставить произвольный Unicode, не трогая раскладку"

Прямого протокольного аналога `KEYEVENTF_UNICODE`/`VK_PACKET` **в ядре X11 (core protocol + XTEST) нет** — X11 core-протокол принципиально построен вокруг пары keycode+modifiers, транслируемой в keysym через активную карту клавиатуры (keymap) сервера; отправить "просто символ" без участия keymap нельзя ни через `XTestFakeKeyEvent`, ни через `XSendEvent`. Единственные два практических обходных пути:

**1. `xdotool type` — временная переподмена свободного keycode.** [веб/код, `raw.githubusercontent.com/jordansissel/xdotool/main/xdo.c`, коммит `5c27b117c91b`, 2026-06-30]

Подтверждено чтением исходника напрямую (я перепроверил, не доверяя выводу WebFetch — вытянул файл `curl`'ом и прогрепал сам):
- `xdo.c:1044-1071`, функция `xdo_send_keysequence_window_list_do` — ищет пустой (незанятый ни одним keysym) keycode в диапазоне `xdo->keycode_low..keycode_high` через `XGetKeyboardMapping`, называет его `scratch_keycode`.
- `xdo.c:1079-1087` — если символу нужен bind (`needs_binding == 1`, устанавливается раньше в `xdo.c:1295-1310` для keysym, отсутствующих в текущей карте): временно переписывает этот keycode на нужный keysym через `XChangeKeyboardMapping(xdo->xdpy, scratch_keycode, 1, keysym_list, 1)`, затем шлёт нажатие через `_xdo_send_key`.
- `xdo.c:1109-1114` — после отправки **откатывает** keycode обратно на пустой keysym (`{ 0 }`) тем же `XChangeKeyboardMapping`.
- Дополнительно нашёл важную деталь, не упомянутую в задании: сама отправка нажатия (`_xdo_send_key`, `xdo.c:1671-1698`) **тоже трогает раскладку**, но на уровне XKB-группы, а не keymap: `XkbGetState`→`XkbLockGroup(xdo->xdpy, XkbUseCoreKbd, key->group)` (заблокировать нужную группу), `XTestFakeKeyEvent(...)`, затем `XkbLockGroup(..., current_group)` (вернуть группу назад) — то есть `xdotool type` для символов вне текущей группы **временно переключает и тут же возвращает XKB-группу на каждый символ**, а не просто ремапит keycode. Это ближе по духу к варианту 2а Mahou (переключение раскладки на лету), чем к "чистой" Unicode-инъекции — просто цикл переключения короче (на уровне libX11-запроса, не системного сообщения).

**2. Ограничения приёма.**
- Гонки при быстром наборе: `XChangeKeyboardMapping`/`XkbLockGroup` — глобальные для X-сервера операции; между `XSync` после ремапа и следующим `XSync` после снятия ремапа (`xdo.c:1084, 1098, 1113`) есть окно, в котором **любой другой клиент**, читающий карту клавиш в этот момент (например, через `XGetKeyboardMapping` или подписку на `MappingNotify`), увидит временное состояние. Само xdotool синхронизируется через `XSync` вокруг каждого символа, что замедляет вставку длинных строк (по одному round-trip к серверу на непримапленный символ) — компромисс "надёжность против гонки" в обмен на скорость.
- Приложения, кеширующие карту клавиш: клиенты X11, которые один раз прочитали `XGetKeyboardMapping` при старте и не переподписаны на `MappingNotify` (или обрабатывают его лениво/с задержкой), могут не заметить временный ремап вовсе, либо наоборот — заметить его и закешировать "неправильный" keysym для scratch-keycode до следующего пересчёта. Это структурно тот же класс проблемы, что у нас с IBus, пересобирающим раскладку.
- XTEST vs uinput: `xdotool` использует XTEST-расширение (`XTestFakeKeyEvent`), то есть события идут через X-сервер и видны всем X-клиентам как обычные события клавиатуры (сервер сам транслирует keycode→keysym по текущей карте в момент доставки). uinput, который использует PuLinto, работает на уровне ядра (evdev), генерируя события до X-сервера — X11 увидит их как события с настоящего физического устройства и применит к ним ту же XKB-карту сервера; отличий в итоговой семантике для этого конкретного приёма (временный ремап keycode) нет — приём одинаково доступен что через XTEST, что через uinput, потому что сам `XChangeKeyboardMapping` — это операция над X-сервером, не над источником события.

**3. Вариант "отдать текст как метод ввода" (IBus/Fcitx commit-text).**

Не проверено кодом в рамках этой задачи (в отличие от xdotool, у меня не было прямого источника с исходниками IBus в этом прогоне) — фиксирую как рассуждение, отталкивающееся от того, что PuLinto уже умеет (`crates/pulinto-layout/src/ibus.rs`, работа через D-Bus с engine/группами, но не через `commit_text`):
- IBus/Fcitx предоставляют отдельный, полностью параллельный XKB, канал доставки текста: движок ввода (`IBusEngine`) может вызвать `commit_text`, и это уйдёт в приложение через input-method-протокол (GTK/Qt IM-модуль или XIM), минуя XKB-трансляцию keycode→keysym целиком — концептуально это ближе всего к Windows `VK_PACKET`/`WM_CHAR`, так как символ уже готов и доставляется, а не собирается из скан-кода.
- Ограничения такого пути: (а) работает только для приложений, реально подключённых к input-method фреймворку (GTK3/GTK4/Qt с IBus/Fcitx IM-модулем) — многие Java/Electron/самодельные toolkit'и или консольные/терминальные приложения либо не имеют активного `InputContext`, либо обрабатывают его непредсказуемо; (б) PuLinto должен быть не просто клиентом шины IBus (как сейчас в `ibus.rs`), а **сам являться IBus-движком** (реализовывать `org.freedesktop.IBus.Engine`), чтобы вызывать `commit_text` от своего лица — это архитектурно другая роль, чем "переключать группу у стороннего движка", которую код делает сейчас (`set_group`, `ibus.rs:204-241`); (в) `commit_text` физически привязан к тому, что приложение сейчас находится в фокусе и IBus считает именно PuLinto активным движком в данный момент — то есть тот же класс гонки "какой движок active" переезжает из проблемы "переключить раскладку" в проблему "переключиться в роль активного engine", просто в другом месте стека.

## Резюме для решения нашей задачи

1. Подозрение задания частично не подтвердилось: Mahou **не** избегает гонки переключения раскладки по умолчанию — оба его "живых" (включенных из коробки) хоткея (`Convert word`/`Convert line`, и `Convert selection` при дефолтном `CSSwitch=true`) переключают системную раскладку и переигрывают скан-коды, то есть подвержены тому же классу гонок, что и PuLinto, и тоже вынуждены городить опрос с таймаутом (`ChangeLayout`, п.4) плюс запасной путь через эмуляцию реальной горячей клавиши.
2. Но Windows-платформа даёт то, чего нет в X11 core-протоколе: канал `KEYEVENTF_UNICODE`→`VK_PACKET`→`WM_CHAR`, который доставляет уже готовый символ в обход трансляции раскладки — Mahou использует его только в одном необязательном режиме (п.2b), но сама возможность в ОС есть безусловно и для GUI-приложений на стандартном цикле сообщений надёжна.
3. У X11 нет протокольного эквивалента этого канала; ближайшие суррогаты — (a) временный ремап свободного keycode (`xdotool type`), который сам по себе не свободен от гонок и требует синхронных `XSync` вокруг каждого непримапленного символа, и при этом ещё и временно дёргает XKB-группу для символов вне текущей раскладки; (b) IME commit-text (IBus/Fcitx), структурно ближе всего к Windows-модели, но требует от PuLinto стать IBus-движком, а не клиентом переключения групп, и работает только в приложениях с активным input-context.
4. Практический вывод: чистого "windows-style" решения на X11 не существует "из коробки" — вариант (a) можно использовать как fallback-приём для отдельных проблемных символов (то, что XKB не даёт напрямую), а вариант (b) — потенциально самый надёжный путь для замены готового слова целиком, но требует более глубокой архитектурной перестройки (роль IBus-движка) и имеет свой собственный класс гонок вокруг "кто сейчас активный движок", а не решает проблему гонок полностью.
