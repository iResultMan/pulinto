## 1. EV_SYN/SYN_REPORT: батчить или нет

Факт из ядра/libevdev: **SYN_REPORT никогда не вставляется автоматически**. `libevdev_uinput_write_event()` — чистый passthrough, дословно:

```c
// libevdev/libevdev-uinput.c:466-489
rc = write(fd, &ev, sizeof(ev));
return rc < 0 ? -errno : 0;
```

никакой логики про SYN там нет **[Ф]**. `interception-tools/uinput.cpp` подтверждает это с другой стороны: их `uinput` просто читает `input_event` из stdin и пишет как есть в `libevdev_uinput_write_event`, полагаясь, что вышестоящий фильтр (`intercept`) уже включил в поток SYN_REPORT — сам бинарник `uinput` синхронизацию не добавляет **[Ф]**. Без SYN_REPORT события остаются "в подвисшем" состоянии на стороне читателя — ни X-сервер, ни libinput не применят изменение состояния клавиши, пока не увидят закрывающий SYN_REPORT (это protocol-level контракт evdev, а не деталь реализации конкретного проекта).

Практика проектов расходится в том, **что именно** попадает под один SYN_REPORT:

- **keyd** (`src/vkbd/uinput.c`, `write_key_event()`) — SYN_REPORT после **каждого отдельного** EV_KEY-события: press → SYN; release → отдельный SYN **[Ф]**. Не батчит вообще ничего.
- **kmonad** (`KMonad/Keyboard/IO/Linux/UinputSink.hs`, `usWrite`) — идентичный паттерн: `send_event ... e` затем сразу `send_event ... sync` на каждый отдельный keyboard-event **[Ф]**.
- **evremap** (`src/remapper.rs`, `emit_keys()`/`write_event_and_sync()`) — **батчит**: при эмуляции комбо или ремапа пишет несколько EV_KEY подряд без промежуточных SYN, и только один `generate_sync_event()` в конце пачки **[Ф]**:
  ```rust
  fn emit_keys(&mut self, key: &[KeyCode], time: &TimeVal, event_type: KeyEventType) -> Result<()> {
      for k in key { let event = make_event(...); self.write_event(&event)?; }
      self.generate_sync_event(time)?;   // один SYN на всю пачку
      Ok(())
  }
  ```
- **ydotool** (`Client/ydotool.c`, `uinput_emit()`) — SYN опционален через явный булев параметр на каждый вызов, решение оставлено клиенту (Daemon просто ретранслирует то, что получил через сокет) **[Ф]**.

**Вывод**: батчинг нескольких EV_KEY под один SYN_REPORT — рабочий и используемый в проде паттерн (evremap делает это стабильно для комбо-клавиш), но для последовательности "разные логические нажатия во времени" (а не один моментальный комбо) доминирующая практика (keyd, kmonad) — один SYN на каждое отдельное press/release. Для цикла Backspace×N + retype это означает: не пытаться отправить N Backspace-press-release под одним SYN — каждое нажатие должно закрываться своим SYN_REPORT, иначе читатель увидит их как один "смазанный" пакет состояния (риск потери промежуточных состояний, особенно если downstream toolkit инспектирует kernel-uровневый поток, что редко для текстовых виджетов, но актуально для мультиплексоров типа libinput/Xorg, которые тоже читают через evdev).

## 3. Гонка со сменой раскладки

Ни один из девяти целевых проектов **сам не переключает раскладку** — это вне их скоупа (все они ремапперы клавиш, а не переключатели языка), поэтому прямых свидетельств "как ждут применения XKB-группы" в их коде нет **[Не найдено]**. Но нашлось два релевантных технических паттерна из соседних областей:

### (a) xdotool — способ полностью обойти гонку, а не ждать её разрешения

`xdo_send_keysequence_window_list_do()` (`xdo.c:1034-1113`) при печати произвольного keysym **не полагается на активную раскладку вообще**: находит неиспользуемый keycode в диапазоне устройства, временно перепривязывает его нужным keysym-ом через `XChangeKeyboardMapping`, обязательно вызывает `XSync()` (это гарантирует X11-протокольный round-trip — сервер применил маппинг до следующего запроса на этом же соединении), затем шлёт `XTestFakeKeyEvent` уже на этот scratch-keycode, снова `XSync()`, и в конце ревертит маппинge обратно **[Ф]**. Это принципиально иной подход, чем "подождать переключения": вместо ожидания активной раскладки инструмент **создаёт свою временную раскладку под конкретный символ**. Работает только на уровне XTest/X11-протокола (клиент управляет X keymap напрямую), неприменимо к чистому uinput/evdev-инжекшену, где интерпретация скан-кода целиком на стороне X-сервера/композитора и клиент не может атомарно привязать к этому событию свой locale keymap.

### (b) keyd — layout-independent канал через Unicode-эскейп (аналог для uinput)

`src/daemon.c` (`input()`) и `src/macro.c` (`MACRO_UNICODE`) для символов вне базовой ASCII-таблицы шлют не «символ в текущей раскладке», а спец-код `KEYD_CANCEL` + hex-цифры кодпоинта (`unicode_get_sequence()`, `src/unicode.c:21-35`) **[Ф]** — это стандартный Ctrl+Shift+U-эскейп, который в IBus/GTK/Qt интерпретируется как «ввести юникод-кодпоинт», **независимо от активной XKB-группы**. Это единственный найденный в проверенных проектах способ инжектировать точный целевой символ через uinput, не заботясь о том, в какой раскладке сейчас клавиатура. Ограничение: работает только там, где активен подходящий input method (не работает в терминалах без такой поддержки, не универсально в Electron/Java-приложениях — прямых тестов в issue-трекерах не найдено **[Не найдено]**).

### (c) Что реально используют clone-проекты автозамены (справочно, детали — в 08)

`xswitcher` (не входит в 9 целевых, но прямой аналог PuLinTo): порядок Backspace → language switcher → retype, с отдельной задержкой на переключение раскладки, автор указывает наблюдаемую задержку **«около 50 мс на KDE»** — фиксированный таймаут по времени, не ожидание подтверждающего события **[Ф, из 08]**. Ни один из найденных clone-проектов не ждёт `XkbStateNotify`.

### (d) Теоретически доступный, но нигде не встреченный путь подтверждения

XKB-расширение предоставляет `XkbStateNotify` с маской `XkbGroupStateMask` (через `XkbSelectEvents`), которое сервер шлёт при фактической смене группы — в теории демон мог бы вызвать `XkbLockGroup()`, затем заблокироваться на приходе `XkbStateNotify` с `state.group == target_group` как на официальном ack, и только затем начинать инжекцию через uinput. **Мы не нашли ни одного проекта (из 9 целевых, ни из смежных clone-проектов в 08), который бы реально так делал** — везде либо фиксированный sleep, либо (для xremap/keyd/kmonad) вопрос вообще не встаёт, так как они не переключают раскладку **[Не найдено]**. Важная оговорка: даже если дождаться `XkbStateNotify`, это подтверждает только то, что **X-сервер** зафиксировал смену группы у своего протокольного состояния — а инжектированное через `/dev/uinput` событие идёт другим путём (ядро → libinput/evdev-драйвер X-сервера → тот же X-сервер), и гарантии строгой цепочки "ack пришёл раньше, чем uinput-событие будет обработано" протоколом не даётся: `XkbStateNotify` летит через X11-сокет, uinput-событие — через отдельный kernel-device-node, это два независимых канала доставки без общего барьера. Практическая рекомендация — не ждать ack как гарантию, а использовать его как **нижнюю границу** ожидания и всё равно добавлять запас по времени.

Точных цифр «сколько реально мс занимает применение XKB-группы» в исходниках 9 проектов и их issue-трекерах **не найдено** **[Не найдено]** — единственное число, всплывшее в разведке, это анекдотическое «~50 мс на KDE» из xswitcher (внешний по отношению к списку проект, см. выше).

## 4. Модификаторы (зажатый Shift/Ctrl/Alt в момент замены)

Два проекта дают конкретный, воспроизводимый паттерн:

**xremap** (`src/event_handler.rs:701-719`, `send_key_press_and_release()`) — эталонная реализация:

```rust
let (mut extra_modifiers, mut missing_modifiers) =
    Self::diff_modifiers(&self.modifiers, &key_press.modifiers);
// extra: физически зажаты, но не нужны для этого символа — снять
// missing: нужны для символа, но не зажаты — прижать
self.send_keys(&missing_modifiers, PRESS);
self.send_keys(&extra_modifiers, RELEASE);

self.send_key(&key_press.key, PRESS);
self.send_key(&key_press.key, RELEASE);
self.send_action(Action::Delay(self.keypress_delay));

// Восстановить исходное состояние модификаторов пользователя
self.send_keys(&extra_modifiers, PRESS);
self.send_action(Action::Delay(self.keypress_delay));
self.send_keys(&missing_modifiers, RELEASE);
```
Три шага: diff → снять лишнее/прижать недостающее → напечатать → **восстановить исходное состояние**, а не просто отпустить всё. `keypress_delay` (по умолчанию 0, конфигурируется `keypress_delay_ms`) стоит по обе стороны восстановления **[Ф]**.

**keyd** (`src/macro.c`, `MACRO_KEYSEQUENCE`) — более простой вариант того же принципа: перед основным кодом прижимает нужные модификаторы (`modifiers[j]` по маске), если задан `timeout` — ждёт между прижатием модификатора и самим символом (`if (mods && timeout) usleep(timeout)`), печатает символ, затем отпускает те же модификаторы **[Ф]**. Не восстанавливает состояние физически зажатых пользователем клавиш отдельно — просто симметрично снимает то, что сам прижал.

Известные баги модификаторов конкретно в этих 9 проектах/трекерах — **не найдено** в рамках разведки (поиск по issue-трекерам не дал релевантных находок с конкретными номерами) **[Не найдено]**. Косвенно релевантен Launchpad bug #837456 про `XTestFakeKeyEvent`, неожиданно сбрасывающий keyboard mapping на 'us' (упомянут в 08) — но это XTest-специфичный баг, не uinput/evdev.

## 5. Автоповтор (EV_KEY value=2)

**keyd** (`src/device.c:509-510`) читает физическое устройство и **отбрасывает** value=2 полностью на входе:
```c
/* Ignore repeat events. */
if (ev.value == 2)
    return NULL;
```
**[Ф]**. Причина: keyd реализует собственную логику авто-повтора для *выходных* макросов через `macro_timeout`/`macro_repeat_timeout` (см. §2), поэтому входные value=2 от физической клавиатуры ему не нужны — он не транслирует их 1:1. Для собственного virtual-device (`vkbd/uinput.c`) при этом регистрируется `EV_REP` (`UI_SET_EVBIT, EV_REP`) **[Ф]** — значит автоповтор для *выходного* устройства генерирует сам input-core ядра на основе состояния удержания клавиши на этом virtual device, а не keyd вручную пересылает value=2.

**evremap** (`src/remapper.rs:320-333`) — иначе: явно **обрабатывает** `KeyEventType::Repeat` (value=2) как отдельный случай в match, для ремапнутых клавиш повторно эмитит `output`-коды с тем же типом `Repeat`, для непереопределённых — прозрачно транслирует через `write_event_and_sync()` **[Ф]**. То есть value=2 не отбрасывается, а участвует в логике ремаппинга наравне с press/release.

**Вывод**: для сценария "стереть слово / напечатать заново" авто-повтор релевантен в основном на **входе** (пользователь мог зажать клавишу, когда сработала замена) — по примеру keyd безопасная практика: игнорировать value=2 входящих событий при принятии решения "менять слово сейчас", реагировать только на переходы 0→1 (press) и 1→0 (release), не давая зажатой клавише повторно триггерить логику замены на каждом autorepeat-тике.

## 6. Собственный ввод: видит ли демон свои же uinput-события

Два принципиально разных, оба рабочих подхода:

### (a) Структурно не подписываться на своё устройство (keyd, kmonad, evremap)

Ни один из этих трёх не читает `/dev/input/event*` вслепую по кругу — они делают `EVIOCGRAB` (эксклюзивный грэб) на **конкретных заранее выбранных физических устройствах** и читают только из них. Их собственный `/dev/uinput`-девайс — отдельный, никогда не открываемый на чтение файл. Обратной связи не возникает **не потому что она фильтруется, а потому что архитектурно нечему замкнуться** **[Вывод из кода всех трёх]**.

### (b) Фильтрация по имени (xremap)

xremap **обязан** так делать, потому что он динамически пересканирует `/dev/input/*` (hotplug, через `platform_linux/device_watcher.rs`) и должен уметь отличить «ещё одну реальную клавиатуру» от «своего собственного virtual device, который он сам только что создал» при повторном скане. Конкретный код (`src/device.rs`):

```rust
pub fn choose_device_name() -> String {
    let name_already_taken = /* есть ли уже устройство с "xremap" в имени */;
    if name_already_taken {
        format!("xremap pid={}", process::id())   // дизамбигуация при повторном запуске
    } else {
        "xremap".to_string()
    }
}
...
pub fn is_input_device(&self, ..., own_device: &str) -> bool {
    if self.device_name() == own_device {
        return false;   // точное сравнение имени — жёсткий фильтр
    }
    ...
}
```
**[Ф]**. Обратите внимание на `choose_device_name()`: если xremap запускается там, где уже есть устройство "xremap" (например, предыдущий процесс не выгрузил uinput-девайс), имя дополняется `pid=<N>`, чтобы не спутать чужой висящий virtual device со своим текущим — то есть фильтрация именно **по точному строковому имени**, и разработчики явно продумали edge-case коллизии имён между разными запусками одного и того же инструмента.

**Вывод для PuLinTo**: раз демон и так читает физическую клавиатуру через `EVIOCGRAB` (эксклюзивный грэб, как в контексте задачи описано), подход (a) уже даёт нужную гарантию бесплатно — grab физического устройства структурно не пересекается с чтением своего virtual uinput-device. Явная фильтрация по имени (b) нужна дополнительно только если где-то в системе (не в самом демоне) есть код, который перечисляет **все** `/dev/input/event*` без разбора (например, вспомогательный watchdog/diagnostic-процесс) — тогда стоит скопировать паттерн xremap: зарегистрировать virtual device с уникальным, легко узнаваемым именем (например, `"PuLinTo virtual keyboard"`) и явным сравнением строки исключать его при любом переборе устройств.

## 7. Скорость инжекции

Прямых чисел "порог, ниже которого гарантированно теряются символы в конкретном тулките (Electron/GTK/Qt/Java)" в исходниках 9 проектов **не найдено** **[Не найдено]** — они не тестируют так глубоко чужие консьюмеры. Что нашлось релевантного:

- **keyd** явно документирует существование проблемы: опция `macro_sequence_timeout` (мкс, per-key) описана как нужная «to avoid overflowing the input buffer **on some systems**» **[Ф]** — то есть без неё на некоторых машинах реально теряются события при быстрой инжекции без пауз. Значение по умолчанию — 0 (выключено), то есть keyd **по умолчанию не троттлит** и полагается на то, что типичная система выдержит.
- Ядро/evdev: клиентский буфер событий на чтение — минимум **64 события** (см. обсуждения `EVDEV_BUFFER_SIZE`/`SYN_DROPPED` в патчах ядра `input: evdev`), при переполнении генерируется `SYN_DROPPED`, и все события текущего пакета до следующего `SYN_REPORT` теряются **[В, по патчам ядра, не по одному из 9 проектов напрямую]**. Для потока "1 клавиша = 1 EV_KEY + 1 SYN_REPORT" этот лимит практически недостижим при разумных задержках — узкое место не в размере kernel-буфера, а в downstream-обработке тулкитом.
- **ibus/ibus#2486** («Keyboard input gets jumbled when typing fast») — подтверждённая (авторами ibus и GTK) проблема именно в применимом сценарии: виджеты, делающие «live processing» на каждое нажатие (например `GtkSearchEntry` с live-фильтрацией по мере ввода), **теряют/путают** символы при быстром вводе, и баг **явно более выражен на X11, чем на Wayland** **[Ф, текст issue]**. Специфической починки в GTK-core нет, только точечные митигации в отдельных приложениях (Nautilus). Это прямое подтверждение, что "быстрая печать ломает live-search-виджеты" — не гипотеза, а открытый баг уровня тулкита.
- Electron/Java — отдельных подтверждений в issue-трекерах **не найдено** в рамках этой разведки **[Не найдено]**; экстраполировать числа с GTK4/ibus на Electron/Java не следует без отдельной проверки.

**Практический вывод**: безопасный ориентир — тайминги из §2 (8-20 мс hold, 2-12 мс между клавишами) покрывают диапазон, реально используемый в проде (ydotool/dotool/xdotool), и это уже выше порога, при котором наблюдался баг в ibus (сам ibus issue не называет число, но проблема "typing fast" подразумевает скорости куда выше, чем 50-100 символов/сек, которые дают тайминги §2).

## 8. Backspace в приложениях с автодополнением/live-search

- **VSCode issue #17025** «Autocomplete triggered on backspace» — подтверждённый, задокументированный баг: последовательность Backspace может **заново открыть/перефильтровать** попап автодополнения, а не просто стереть символ **[Ф, из issue]**. Для сценария массового Backspace (стереть N символов) это значит: каждое отдельное нажатие Backspace потенциально триггерит UI-работу (перерисовка попапа), которая добавляет задержку обработки и может съедать следующие в очереди события, если инжекция идёт быстрее, чем успевает отработать UI-thread.
- **ibus/ibus#2486** (см. §7) — тот же корень: виджеты с live-processing на каждое нажатие (поиск-по-мере-ввода) страдают при быстром вводе; логично, что они так же уязвимы и к быстрому **удалению** (Backspace тоже нажатие, тоже триггерит live-filter).
- Специфика readline/терминала (GNU readline, bash/zsh) — отдельного подтверждённого источника в рамках разведки **не найдено** **[Не найдено]**; это не значит, что проблемы нет, значит, что мы не нашли задокументированный кейс с числами в открытых трекерах за отведённое время.

**Вывод**: главный подтверждённый риск — не потеря самих Backspace-событий, а то, что каждый Backspace может быть недёшев для приложения (пересчёт автодополнения/live-search), и это возвращает нас к необходимости пауз между Backspace-ами того же порядка, что и между обычными символами (см. §2), а не более быстрого "спецрежима для удаления".

## Рекомендации для PuLinTo

Исходя из совокупности находок выше:

**Последовательность событий при замене слова:**

1. Зафиксировать целевое количество Backspace = длина буфера скан-кодов текущего слова (+ разделитель, если он тоже уводится под замену — вопрос покрыт в 08, здесь не переисследовался).
2. Снять модификаторы по паттерну xremap (§4): вычислить diff между реально зажатыми (физически удерживаемыми пользователем в момент старта замены) и нужными для инжекции; отпустить лишнее, но **запомнить**, что было лишним, чтобы вернуть после.
3. Каждый Backspace — отдельная пара `EV_KEY(KEY_BACKSPACE, 1)` + `SYN_REPORT`, затем `EV_KEY(KEY_BACKSPACE, 0)` + `SYN_REPORT` — **не батчить несколько Backspace под один SYN** (см. §1: батчинг оправдан только для одномоментных комбо, не для последовательности во времени).
4. Между каждой парой press/release Backspace — задержка **8-20 мс** (диапазон ydotool/dotool, §2); между полным press+release одного Backspace и следующим — те же 2-12 мс, что и между обычными символами (§8: Backspace не «дешевле» обычного символа для приложения).
5. Переключить раскладку (XKB group) и добавить фиксированную задержку **не менее ~50 мс** (единственная найденная цифра, xswitcher/KDE, §3) как нижнюю границу, поскольку никакой протокольно-надёжный ack между независимыми каналами (X11-сокет для XKB и kernel-node для uinput) не гарантирован (§3d) — ждать `XkbStateNotify`, если он реализован, но **не полагаться** на него как на единственную гарантию, оставлять запас по времени сверху.
6. Печатать целевые скан-коды той же парой press/release + SYN на каждое нажатие, с теми же 8-20 мс hold / 2-12 мс delay, восстанавливая Shift для тех символов, где он нужен, по месту (не держать Shift зажатым на всё слово, если не все буквы его требуют — иначе исказится регистр там, где Shift не нужен).
7. После окончания слова — вернуть исходное состояние модификаторов, которые были физически зажаты пользователем и которые демон снимал в шаге 2 (симметричное восстановление, как в xremap `send_key_press_and_release`, §4), с той же паузой в 8-20 мс до восстановления.

**Синхронизация со сменой раскладки** — решено не через строгий ack (никто из проверенных проектов так не делает, и такой ack в принципе не покрывает оба независимых канала доставки), а через: (i) минимальную эмпирическую задержку ≥50 мс после инициации переключения, (ii) по возможности — layout-independent канал для критичных символов по образцу keyd (Ctrl+Shift+U + hex codepoint) как fallback для приложений, где это поддерживается, что делает результат корректным вне зависимости от того, успела ли раскладка примениться.

**Фильтрация собственного ввода** — если демон уже делает `EVIOCGRAB` на конкретных заранее известных физических устройствах и не сканирует `/dev/input/*` вслепую, отдельная фильтрация не нужна (структурная гарантия, как в keyd/kmonad/evremap, §6). Если где-то в PuLinTo есть код, перечисляющий все input-устройства без разбора (диагностика, hot-reload конфига устройств), скопировать паттерн xremap: уникальное самоидентифицирующее имя virtual-device (`"PuLinTo virtual keyboard"`) + точное строковое сравнение при любом переборе, с дизамбигуацией по PID на случай не выгрузившегося предыдущего процесса.

**Автоповтор** — игнорировать value=2 при решении "стартовать замену сейчас" (реагировать только на 0→1/1→0 переходы, как в keyd, §5); на выходном virtual-device регистрировать `EV_REP`, чтобы автоповтор для последующего обычного набора генерировался ядром, а не вручную.
